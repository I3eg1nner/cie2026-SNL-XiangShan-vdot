## P5　阶段一到阶段二的桥：vdot 应该放在哪里

- **标题**：从 vadd 到 vdot——「切断跨段进位」与「打通跨段求和」
- **要点**
  - `vadd.vv` 的 64 位加法链按 SEW 在段边界**切断**进位；vdot 需要的恰好相反——跨 16 个元素**打通**求和
  - 译码 → 拆分 → 重命名 → 分发 → 发射 → 写回这条控制骨架，vdot 可以完全复用
  - 落点选 `FuType.vimac` / `VIMacU`：昆明湖 V2 上 16 路 8×8 有符号乘法阵列唯一的现成实现就是 `VIMacU` 内 2 片 `VIMac64b`；`VIPU`/`VIAlu` 内没有乘法器
  - 不新增 `FuType`：`FuType` 是 one-hot 枚举，加一项会加宽 IQ / ROB / 旁路网络的字段
- **推荐配图**：自绘对比图（左：vadd 8 段独立加法链；右：vdot 16 积跨段归约），依据 `docs/stage1/02_向量加法指令执行过程分析.md:1143` 与 `:1152-1155`
- **证据出处**：桥接结论 `docs/stage1/02_向量加法指令执行过程分析.md:1152-1155`；落点理由表 `docs/stage2/10_vdot指令设计文档.md:452-461`
- **讲者备注**（约 45 秒）：阶段一的波形分析直接决定了阶段二的落点。我们在波形上看到 vadd 的加法器按 SEW 把进位链切断，而 vdot 要做的正好相反，是把 16 个乘积跨段加起来。所以控制骨架可以全部复用，要新建的只是归约数据通路。点积最贵的部件是乘法阵列，昆明湖 V2 上唯一现成的就在 VIMacU 里，所以我们把 vdot 挂在 VIMacU 上，而不是新开一个功能单元类型。

## P6　阶段二：指令定义

- **标题**：vdot 指令族——一条赛题指令 + 两条共享数据通路的扩展
- **要点**
  - `vdot.vv`：funct6 `111001`，SEW=8，16 路 int8×int8 归约到 `vd.u32[0]`
  - `vdotacc.vv`：funct6 `111010`，累加变体（`vd[0] += Σ`），消除长向量循环里的独立累加指令
  - `vdot4a.vv`：funct6 `111011`，SEW=32 下 4 组×4 路分组点积累加（对标 Zvqdotq / ARM SDOT / x86 VPDPBUSD 风格）
  - 溢出证明：16 项和 |Σ| ≤ 262144 = 2^18 < 2^31，`vdot.vv` 不需要饱和逻辑
  - 语义裁定 S-1…S-9 写进 C 参考模型 `tests/golden/vdot_ref.c`，全项目唯一语义来源；编码空间由脚本证明未被 RVV 1.0 占用
- **推荐配图**：自绘编码位域图（依据 `docs/stage2/10_vdot指令设计文档.md:38-59`）
- **证据出处**：指令族总览 `docs/stage2/10_vdot指令设计文档.md:26-30`；溢出 `10:308-311`；裁定表 `docs/_plan/MASTER_PLAN.md:37-46`；编码证明 `10:358` 起、`logs/stage2/check_funct6.log`
- **讲者备注**（约 50 秒）：赛题要求的是 vdot.vv，SEW 等于 8、VLEN 等于 128，也就是 16 个 int8 乘积求和。我们另外定义了两条扩展：累加版 vdotacc 面向长向量循环，分组版 vdot4a 面向 SEW=32 的分组点积，用来体现扩展能力。三条指令共用同一套硬件。我们先证明了 vdot.vv 不可能溢出，所以不需要饱和逻辑；再把 vstart、掩码、尾部这些边角行为逐条裁定，写进一个 C 参考模型，后面所有测试平台都直接包含它，不重写语义。

## P7　微架构亮点一：最大限度复用

- **标题**：零新增乘法阵列，`FuConfig` 等一行未改
- **要点**
  - 16 路 8×8 乘法阵列**零新增**：直接取 2 片 `VIMac64b` 的部分积，只加一个只读输出端口 `prod16`（`VIMac64b.scala` +7 行）
  - 加法树全部例化 YunSuan 既有原语 `CSA4to2` / `CSA3to2`（12 + 4 个实例）
  - **`FuConfig` / `FuType` / `Parameters` / Dispatch / IQ / WbArbiter 一行未改**；vdot 挂在既有 `VimacCfg`（`CertainLatency(2)` 不变）上
  - 零回归三重证据：9 个既有 FU 输出与 pristine 逐字相同；164 个共有 module 中 163 个去注释后逐字节相同（差异仅 `SimTop`）；`vmul`/`vwmul`/`vmacc` 数据成形拍仍为 2 拍
  - 新增算术逻辑约 **13.7%**（全加器等价结构计数**上界**，非综合结果）
- **推荐配图**：自绘模块层次图，复用件灰色、新增件高亮（依据 `docs/stage2/10_vdot指令设计文档.md:467-513`）
- **证据出处**：`README.md:63-69`；复用清单 `docs/stage2/10_vdot指令设计文档.md:971-985`；一行未改 `docs/stage2/11_RTL实现说明.md:30`；163/164 `logs/stage2/p5_regression.log:52-53`；13.7% `10:1020-1023`、`10:997`
- **讲者备注**（约 55 秒）：赛题明确要求复用昆明湖 V2 的向量实现，这也是我们最看重的一点。点积单元里最贵的是乘法阵列，我们一个都没造，而是从现有的两片 VIMac64b 里把 16 个乘积引出来，只加了一个只读端口。加法树用的也是 YunSuan 现成的压缩器原语。更重要的是调度相关的配置一行没改，延迟仍是 2 拍，所以发射、唤醒、写回网络完全不受影响。我们用三种方式证明没有破坏既有指令。13.7% 这个数是从结构里数出来的上界，没做综合，这一点我们在局限里也会说。

## P8　微架构亮点二：XOR 蝶形折叠加法树

- **标题**：一棵树、两种形态——2 bit `foldLevels` 控制的 XOR 蝶形折叠
- **要点**
  - 同一组 **12 个 `CSA4to2(32)`** 同时覆盖「16 路全归约」（vdot/vdotacc，`foldLevels=2`）与「4 组×4 路」（vdot4a，`foldLevels=0`）
  - 伙伴 lane 取 `g XOR Δ`（Δ=1、2）：每个 lane 做完全相同的运算，全折叠时 4 个 lane 都持有总和，**元素 0 定位无需额外选择逻辑**
  - 结果路径上**零选择器**：模式切换只作用在加数输入端的 AND 门（512 个 2 输入 AND），不增加关键路径
  - 波形直接证据：全 `0x80`×`0x80` 时 `io_dotVd` 的 4 个 lane 都是 `0x40000`（262144）
  - 向更大 VLEN 扩展只需增加折叠级数，结构不变
- **推荐配图**：自绘蝶形结构图（依据 `docs/stage2/10_vdot指令设计文档.md:812-855`）+ `docs/stage2/figures/fig1_vdot_wave.png`
- **证据出处**：设计 `docs/stage2/10_vdot指令设计文档.md:808`、`:866-880`；波形 `docs/stage2/12_基础功能测试报告.md:843`
- **讲者备注**（约 55 秒）：这是我们认为最有特色的设计。vdot 要把 16 个乘积加成 1 个数，vdot4a 要加成 4 个独立的数。朴素做法是造两棵树再用选择器选，我们用一棵树加一个两位的折叠控制信号解决。每一级的伙伴 lane 用异或算出来，所以 4 个 lane 做的事完全一样，全折叠时每个 lane 最后都是总和，直接取 lane 0 就行，结果路径上一个选择器都没有。大家看这张波形，全负数最大值输入时，四个 lane 都是 262144，这就是蝶形结构的直接证据。

## P9　微架构亮点三：三指令共享一条数据通路，延迟保持 2 拍

- **标题**：三条指令同一乘法阵列、同一棵树，只差 `foldLevels` 与累加注入
- **要点**
  - 区别只在两处：`foldLevels`（0 / 2）与累加操作数注入（vdotacc 只注入 lane 0，vdot4a 注入 4 个 lane）
  - 延迟保持 2：从 `sum_wo` 抽头，加法树跨 S1/S2 切分（方案 B）；把延迟提到 3 的方案 C 被否决——那会让 `vmul`/`vmacc`/`vwmacc` 等十几条既有指令集体慢一拍
  - 为什么塞得下：`vimac` 的时钟周期由 SEW=64 工况决定，SEW=8 时 S1/S2 有大量逻辑级裕量（**静态估算，非综合结果**）

## P12　阶段三：NEMU↔RTL 协同仿真机制

- **标题**：Level 1 协同仿真——REF 原样取自全核 difftest，DUT 换成译码单元 + vdot 功能单元
- **要点**
  - REF：`dlopen` 真实 `riscv64-nemu-interpreter-so`，经 difftest 原生 C API（`difftest_memcpy` / `regcpy` / `exec`）逐条驱动；平台内**不含任何 vdot 语义代码**
  - DUT：Verilated `VDotTop`（值）+ `VdotDecodeProbe`（例化真实 `DecodeUnit` + `VecExceptionGen`，判非法）
  - 激励 **72758** 条（定向 30758 + 架构内随机 30000 + 非法面随机 12000）：值比对 **55924/55924**，非法判定合法一致 55924、非法一致 16834、**分歧 0**

- **讲者备注**（约 60 秒）：协同仿真我们做的是 Level 1。参考端完全照搬全核 difftest：加载真实的 NEMU 共享库，用 difftest 自己的 C 接口一条条喂指令；被测端不是整个乱序核，而是香山真实的译码单元加上 vdot 功能单元。所以它能证明 NEMU 和香山 RTL 对每条 vdot 算出同样的值、对同样的非法情况报异常，七万多条激励，值 0 失配、判定 0 分歧。它证明不了指令在流水线里被正确发射和提交，那需要全核 difftest。这里还有个真实的坑：NEMU 按 PC 缓存译码结果，我们必须先执行 fence.i 才能让它重新译码。

## P18　敏感性分析与一个不利发现

- **标题**：2.00× 的敏感性区间 1.00×–5.00×，以及本方案的最大威胁

- **证据出处**：`bench/results/sensitivity.csv:2-8`；`docs/stage3/22_基线实现与延迟加速分析.md:661-678`；不利发现 `22:635-652`；`README.md:55-57`
- **讲者备注**（约 55 秒）：2 倍这个模型值依赖几条假设，我们逐条放宽算了一遍。最悲观的情况是 vdot 延迟退化到 4 拍，那时优势完全消失；最乐观的 5 倍我们不采用，因为没有证据支持。我们还主动报告一个对自己不利的发现：vdotacc 在循环里的携带依赖是 2 拍，比基线的宽加法 1 拍更长，如果软件不做累加器展开，长向量吞吐可能反而下降。我们已经交付了两路累加器的版本，但真实周期数要等全核仿真才能回答，这是我们结论的最大不确定来源。

## P19　代价与扩展潜力

- **标题**：花了多少钱，还能往哪里扩
- **要点**
  - 代价：新增算术逻辑约 13.7%（结构计数上界）+ 256 bit 触发器；既有 `vmul`/`vwmul`/`vmacc` 数据仍在第 2 拍成形（实测）；未综合，频率影响未知
  - 更高 SEW：`vdot4a` 已在 SEW=32 下工作；SEW=16 源元素只需参数化宽度与级数
  - 更大 VLEN：`VIMacU` 的乘法片数随 VLEN 参数化；VLEN=256/512 时折叠级数 2 → 3 → 4，蝶形结构允许在任意级间插寄存器
  - LMUL>1：方案（uop0 = `vdot`，后续 uop = `vdotacc` 累加链）已在设计文档论证并给出源码证据，**未实现**
  - 其它归约 / 分组粒度：`foldLevels` 加宽即可表达 2/4/8/全路分组
- **推荐配图**：自绘「VLEN 128 → 256 → 512 时折叠级数」小表（依据 `docs/stage2/10_vdot指令设计文档.md:1320-1335`）
- **证据出处**：代价 `docs/stage3/22_基线实现与延迟加速分析.md:692-700`、`:711-720`；扩展 `docs/stage2/10_vdot指令设计文档.md:1309-1335`；LMUL>1 `10:1337` 起
- **讲者备注**（约 45 秒）：一个没有标出代价的加速比不是工程结论。我们的代价是约 13.7% 的新增算术逻辑上界和 256 位触发器，既有指令一拍没慢。扩展方面，vdot4a 已经在 SEW=32 下工作；VLEN 变大时，乘法阵列本来就随 VLEN 参数化，蝶形树只需要多加折叠级。LMUL 大于 1 的方案我们论证过，但这一版没有实现。
