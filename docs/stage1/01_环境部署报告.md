## 1. 官方规定的部署流程（以 `xs-env` 为准）

香山官方的前端开发环境部署仓库是 `OpenXiangShan/xs-env`（本地 `work/xs-env`，
commit `81346b8de58d9d6f5d944d1d720c1be4d85d1ebb`）。它规定的标准流程是：

```sh
git clone https://github.com/OpenXiangShan/xs-env
cd xs-env
sudo -s ./setup-tools.sh   # apt 装依赖
source setup.sh            # 初始化子模块 + 设环境变量
source ./env.sh            # 每次使用前设环境变量
```

拆开看，`xs-env` 实际做了四件事（`work/xs-env/README.md`、`setup-tools.sh`、`install-scripts/`）：

1. **系统依赖**（`install-scripts/base.sh`）：`git make g++ libreadline6-dev libsdl2-dev
   g++-riscv64-linux-gnu zlib1g-dev device-tree-compiler flex autoconf bison
   libsqlite3-dev libzstd-dev python3 ...`。这一组正是 NEMU 构建所需。
2. **LLVM 工具链**（`install-scripts/llvm.sh`）：从 apt.llvm.org 装 clang-19（Ubuntu 24.04 自带的
   clang-18 对 gsim 与 Verilator 5.05x 太旧）。
3. **JDK / mill / Verilator / gsim**（`jdk.sh` / `mill.sh` / `verilator.sh` / `gsim.sh`）：
   GraalVM JDK 21 + mill 1.0.4 + Verilator v5.052 源码自建 + gsim 预编译二进制。
4. **环境变量**（`env.sh`）：
   `NEMU_HOME=$XS_PROJECT_ROOT/NEMU`、`AM_HOME=$XS_PROJECT_ROOT/nexus-am`、
   `NOOP_HOME=$XS_PROJECT_ROOT/XiangShan`、`DRAMSIM3_HOME=$XS_PROJECT_ROOT/DRAMsim3`。

官方的自检脚本 `env-test.sh` 的流程是：编译 NEMU 的 `riscv64-nutshell-ref_defconfig` →
用 NutShell（而不是香山）跑 `make verilog` / `make emu` / `./build/emu -i microbench.bin`。
也就是说，**官方自己也是用一个规模小得多的核来验证环境可用性的**，并不要求一上来就编全核香山。
本项目的分层验证策略（MASTER_PLAN D3）与这一思路一致。

官方同时提供了 `work/xs-env/Dockerfile`（`ARG BASE_IMAGE=ubuntu:24.04`），把上面四步拆成多个
RUN 层以复用缓存。本项目的镜像就是在它的基础上做的裁剪，见第 2 节。

### 本机相对官方流程的三处偏离（及理由）

| 偏离 | 做法 | 理由 |
|---|---|---|
| 不在宿主机 `sudo ./setup-tools.sh` | 改为在 Docker 容器里装依赖 | 宿主是 macOS 15.5 / arm64，没有 apt；NEMU 是面向 Linux 的（`-lreadline`、`-lSDL2`、`memfd`/`mmap` 路径），放容器里最省事也最可复现 |
| 不装 JDK / mill / Verilator / gsim | 镜像里刻意不含 | 这四样属于硬件侧工程师的职责，且他在宿主机原生 arm64 上跑（Verilator 原生比容器快）；镜像不含它们可把体积从 ~6 GB 压到 2.78 GB、构建时间减少一大半 |
| 不用 `xs-env` 的子模块布局 | 直接用独立克隆的 `work/NEMU`，`NEMU_HOME` 显式指向它 | `work/xs-env` 的子模块目录（`NEMU/`、`XiangShan/`、`nexus-am/`、`DRAMsim3/`、`NutShell/`）全是空的，没有 `git submodule update --init`；本项目的 `work/NEMU` 已是按 MASTER_PLAN D1 选定的 `master` 分支浅克隆，再拉一份只会浪费空间 |

## 2. 容器镜像设计（`scripts/docker/Dockerfile.xsdev`）

镜像名 `xsdev:ubuntu24.04-arm64`，体积 **2.78 GB**，
ID `sha256:e6437c4c6d1087173ad2a55621b00f3cb60a84ef1180e9bfffabe44b74900039`。

### 2.1 基础镜像为什么选 Ubuntu 24.04

本项目后面要写的是 RVV 1.0 的向量点积指令，测试程序必须能用 `-march=rv64gcv_zve64x` 编译。

- Ubuntu 22.04 的 `binutils` 是 2.38、GCC 11，对 RVV 1.0（2021 年底才冻结）的支持不完整；
- Ubuntu 24.04 arm64 的 apt 直接提供 **binutils 2.42** 与 **GCC 13.2/13.3/14.2 级别**的
  RISC-V 交叉工具链，`vsetvli / vle8.v / vadd.vv / vse8.v` 全部可汇编。

实测 apt 候选版本（`apt-cache policy`，linux/arm64）：

```
gcc-riscv64-unknown-elf:      13.2.0-11ubuntu1+12
gcc-riscv64-linux-gnu:        4:13.2.0-7ubuntu1     (实际装到 13.3.0-6ubuntu2~24.04.1)
gcc-14-riscv64-linux-gnu:     14.2.0-4ubuntu2~24.04.1cross1
binutils-riscv64-unknown-elf: 2.42-1ubuntu1+6
```

因此**不需要**去下载第三方预编译 riscv-gnu-toolchain 压缩包，也**不需要**退到 clang
`--target=riscv64`。apt 的工具链就够用。

### 2.2 为什么是原生 linux/arm64，而不是模拟 amd64

Docker Desktop 的 Linux VM 本身就是 aarch64（`docker info` → `Architecture: aarch64`）。
NEMU 源码里的 x86 intrinsic（SSE/AVX 相关）全部被 `__x86_64__` 宏保护，aarch64 下走通用 C 路径，
不需要任何改动即可编译——这一点在第 3 节由实际构建结果证实（**零 patch**）。
原生运行比模拟快约 1.7 倍以上（实测数据见第 6 节），没有理由模拟。

### 2.3 分层与依赖取舍

| 层 | 内容 | 对应 `xs-env` 出处 |
|---|---|---|
| 1 | `build-essential cmake ninja-build bison flex git curl libreadline-dev libsdl2-dev libz-dev libncurses-dev libsqlite3-dev libzstd-dev device-tree-compiler python3 ...` | `install-scripts/base.sh` 的 NEMU 相关子集 |
| 2 | `gcc-riscv64-linux-gnu` / `g++-riscv64-linux-gnu` / `gcc-14-riscv64-linux-gnu` / `gcc-riscv64-unknown-elf` / `binutils-riscv64-unknown-elf` / `picolibc-riscv64-unknown-elf` | `base.sh` 只装了 `g++-riscv64-linux-gnu`，这里补齐裸机与 GCC 14 备选 |
| 3 | **RVV 1.0 自检**（见下） | 本项目新增 |

逐项依赖理由（可在 `work/NEMU/Makefile` 中核对）：

- `libreadline-dev` → `NEMU/Makefile:120` 非 SHARE 构建链接 `-lreadline -ldl`（sdb 交互命令行）；
- `libsdl2-dev` → `NEMU/Makefile:125-128` 开了 `CONFIG_DEVICE` 且非 SHARE 时链接 `-lSDL2`
  （kmhv2 独立配置启用了 VGA/keyboard，见 `configs/riscv64-xs-kmhv2_defconfig` 的
  `CONFIG_HAS_VGA=y` / `CONFIG_HAS_KEYBOARD=y`；`CONFIG_VGA_SHOW_SCREEN` 未开，所以不需要 X11/显示器）；
- `libz-dev` → `NEMU/Makefile:116` 的 `-lz`（SHARE 构建则在 `scripts/build.mk:7`）；
- `bison` / `flex` → `NEMU/tools/kconfig` 生成 `conf`/`mconf` 时需要（`scripts/config.mk:35-43`、`:51-53`）；
- `git` → NEMU 的 `scripts/softfloat.mk:6-8` 等会在 make 解析阶段自动 `git clone` 第三方源码；
- `device-tree-compiler` / `python3` / `cmake` / `ninja-build` → 对齐 `xs-env` 的 base，
  供后续阶段（生成 dtb、跑 NEMU 的辅助脚本）使用。

### 2.4 镜像构建期强制 RVV 1.0 自检

Dockerfile 第 3 层不是装软件，而是**在构建期证明工具链真的能汇编 RVV 1.0**：
写一段含 `vsetvli / vle8.v / vadd.vv / vse8.v` 的汇编，用 `-march=rv64gcv_zve64x -mabi=lp64d`
编译，再 `objdump -d | grep -q 'vadd\.vv'` 确认机器码里真有这条指令。任何一步失败，
`docker build` 当场失败，不会产出一个"看着能用、其实编不了向量指令"的镜像。

真实输出（`logs/stage1/p1_docker_build.log:1995`）：

```
#8 0.162 RVV 1.0 assembler probe OK: riscv64-linux-gnu-gcc (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0
```

## 4. 阶段一 1.1 验证信息输出

要求输出：`hello xiangshan, I am cie2026-vdot, IP address <本机IP>`，
且必须是**模拟器实际执行 RISC-V 程序**产生的，不是 shell `echo`。

入口：`./scripts/03_run_hello.sh`，日志 `logs/stage1/p1_hello_xiangshan.log`。
源码：`tests/riscv/hello/`（`start.S` + `hello.c` + `hello.ld.in` + `Makefile`）。

### 4.1 输出通路的选型：为什么不用 nexus-am

NEMU 跑裸机程序有三条路：

| 路线 | 做法 | 本项目是否采用 |
|---|---|---|
| (a) AM（nexus-am） | 用 `AM_HOME` 下的抽象机器库，程序调 `putch()`，由 AM 的 `nemu` 平台代码写串口 | **否** |
| (b) 直接写串口 MMIO | 程序自己往 NEMU 的串口设备寄存器写字节 | **是** |
| (c) 写 FLASH/VGA/帧缓冲 | — | 否 |

不走 (a) 的理由：`work/xs-env/nexus-am` 是**空目录**（子模块未初始化），走这条路要先
`git submodule update --init nexus-am`，再为 `ARCH=riscv64-nemu` 构建 AM 库，引入一整套
额外依赖与版本耦合；而本阶段只需要打印一行字符串，(b) 的代价是十几行代码，且
**更能说明问题**——程序直接操作的就是 NEMU 的设备模型地址。

NEMU 在 `riscv64-xs-kmhv2_defconfig` 下提供两个串口（见 defconfig）：

| 设备 | MMIO 基址 | 说明 |
|---|---|---|
| UARTLITE | `0x40600000` | 寄存器布局见 `NEMU/src/device/uartlite.c:19-23`，TX FIFO 偏移 `0x4`（`uartlite.c:21`） |
| UART16550 | `0x310b0000` | `CONFIG_UART16550_REG_SHIFT_2` |

本程序选 UARTLITE：往 `0x40600004` 写 1 字节，NEMU 的 `serial_io_handler`
（`NEMU/src/device/uartlite.c:126-129`）把它 `putc(..., stderr)` 转发到宿主终端。
`CONFIG_ENABLE_CONFIG_MMIO_SPACE=y` 且 `CONFIG_MMIO_SPACE_RANGE="0x0, 0x7FFFFFFF"`，
所以 `0x40600004` 落在 MMIO 空间，不会被当成普通内存。

### 4.2 启动与退出：复位路径和 nemu_trap

`riscv64-xs-kmhv2_defconfig` 设了 `CONFIG_RESET_FROM_MMIO=y`、
`CONFIG_MMIO_RESET_VECTOR=0x10000000`，所以 NEMU 的 PC 从 FLASH 开始
（`NEMU/src/isa/riscv64/init.c:55-57`，日志 `p1_hello_xiangshan.log:103` 有
`NEMU will start from pc 0x10000000`）。FLASH 的内容由
`CONFIG_FLASH_PRESET_CONTENT="0x74446073,0x0010029b,0x02a29313,0x30033073,0x01f29293,0x00028067"`
提供，反汇编即：

```
csrrsi  x0, mnstatus, 4     # 置 NMIE
addiw   x5, x0, 1
slli    x6, x5, 42
csrrc   x0, mstatus, x6     # 清 mstatus.MDT (bit 42, Smdbltrp)
slli    x5, x5, 31          # x5 = 0x8000_0000
jalr    x0, 0(x5)           # 跳到 CONFIG_MBASE
```

因此程序必须链接到 `CONFIG_MBASE = 0x80000000`，入口第一条指令就是 `_start`。
NEMU 把 image 原样读进 pmem 起始处（`NEMU/src/monitor/image_loader.c:281-282`），
所以交付给 NEMU 的是 `objcopy -O binary` 出来的扁平 bin，不是 ELF。

退出用 NEMU 自带的 `nemu_trap` 指令，编码 `0x0000006b`：

```
NEMU/src/isa/riscv64/instr/decode.c:107
  def_INSTR_TAB("0000000 00000 ????? 000 00000 11010 ??", nemu_trap);
NEMU/src/isa/riscv64/instr/special.h:36-52
  a0 ∉ {0x100, 0x101} 时走 HOSTCALL_EXIT，a0 作为退出码
```

`start.S` 里 `li a0, 0` 后 `.word 0x0000006b`，于是 NEMU 打印 `HIT GOOD TRAP`。

另外 NEMU 复位后 `mstatus.FS = mstatus.VS = 0`（Off，见 `init.c:72-73`），
不先把它们置位，`vsetivli` 和 `csrr vlenb` 都会触发非法指令异常，
所以 `start.S` 开头有 `li t0, (3<<13)|(3<<9); csrs mstatus, t0`。

### 4.3 本机 IP 怎么来的

**不能**直接用 `ipconfig getifaddr en0`：本机 en0 没拿到 DHCP 租约，返回的是
`169.254.137.112`，是链路本地（APIPA）自配地址，不是可路由的真实 IP。
正确做法是先问默认路由走哪块网卡，再取那块网卡的地址：

```bash
iface=$(route -n get default | awk '/interface:/{print $2}')   # -> en1
ipconfig getifaddr "$iface"                                     # -> 192.168.30.213
```

日志 `p1_hello_xiangshan.log:7-12` 记录了这三条命令的真实输出，包括
`ifconfig en1 | grep 'inet '` 的交叉验证：
`inet 192.168.30.213 netmask 0xfffffe00 broadcast 192.168.31.255`。

这个值由 `scripts/03_run_hello.sh` 在**宿主机**上探测（容器里探到的是容器 IP，没有意义），
通过 `make HOST_IP=...` 传进去，再由 `tests/riscv/hello/Makefile` 生成
`build/nemu_config.h` 中的 `#define HOST_IP "192.168.30.213"`，**编译期固化进 RISC-V 程序的只读数据段**。

### 4.4 横幅怎么做到"自证来自模拟器"

验证程序打印的横幅分两部分：

1. **编译期从 NEMU 实际构建配置里抽出来的常量**。`tests/riscv/hello/Makefile` 不是写死地址，
   而是从 `$(NEMU_HOME)/include/generated/autoconf.h` 里 grep `CONFIG_MBASE`、
   `CONFIG_UARTLITE_MMIO`，从 `src/isa/riscv64/instr/rvv/vreg.h` 里 grep `VLEN`，
   再生成 `build/nemu_config.h`。链接地址同样由 `CONFIG_MBASE` 替换 `hello.ld.in` 的 `@MBASE@` 得到。
   也就是说，**只要这些值和实际构建的 NEMU 对不上，程序连一个字符都打不出来**。
2. **运行期从模拟器实读的机器状态**：`mvendorid`、`marchid`、`mimpid`、`misa`、`vlenb`
   全部由 `csrr` 读出。宿主机无法伪造这些值——它们来自
   `NEMU/src/isa/riscv64/init.c:193`（`vlenb->val = VLEN/8`）与 `init.c:233-235`（`mvendorid`/`marchid`/`mimpid`）。

并且程序会把两者**交叉校验**：`csrr vlenb × 8` 是否等于编译期抽到的 `VLEN` 宏，
输出 `VLEN cross-check: MATCH`。

此外还顺手跑了一段 RVV 1.0 向量加法自检（`vsetivli t0,16,e8,m1,ta,ma` + `vadd.vv`，
含负数输入），把 `vs2 / vs1 / vd` 三个向量都打出来并与 C 参考值逐元素比对，
既证明了工具链能编 RVV、也证明了 NEMU 能执行 RVV，为阶段一的
"向量加法指令执行过程分析" 和后续的 vdot 扩展打底。

## 5. 遇到的真实问题与解决

### 5.1 NEMU 的 `.config` 是全局状态，两种形态会互相覆盖

**现象**：NEMU 两种形态共用同一个工作区。`make <defconfig>` 会重写 `.config` 和
`include/generated/autoconf.h`。先建独立、后建 ref，收尾状态就是 ref 配置——而
`riscv64-xs-kmhv2-ref_defconfig` 把**所有串口设备都关掉了**
（`# CONFIG_HAS_UART16550 is not set`、`# CONFIG_HAS_UARTLITE is not set`），
于是验证程序的 Makefile 从 `autoconf.h` 里抽不到 `CONFIG_UARTLITE_MMIO`。

**真实复现与拦截**（`logs/stage1/p1_hello_config_guard.log`）：

```
### 1) 把 NEMU 配置切到 difftest ref
$ grep -c CONFIG_UARTLITE_MMIO include/generated/autoconf.h
0

### 2) 此时去构建验证程序
$ make NEMU_HOME=/work/work/NEMU HOST_IP=192.168.30.213
make: *** [Makefile:51: check-config] Error 1
ERROR: 当前 NEMU 配置没有 CONFIG_UARTLITE_MMIO（difftest ref 配置关掉了所有串口设备）。请切回 riscv64-xs-kmhv2_defconfig
make 退出码 = 2
```

**解决**：两手。
(1) `tests/riscv/hello/Makefile` 加 `check-config` 目标，抽不到任何一个必需值就立刻失败并给出
可操作的提示，绝不用默认值蒙混过去；
(2) `scripts/02_build_nemu.sh` 在 `all` 模式末尾追加 **[C] 恢复独立解释器配置** 这一步
（`p1_nemu_build.log:231`），保证脚本跑完后工作区是"可以直接跑 RISC-V 程序"的状态。

### 5.2 `ipconfig getifaddr en0` 给出的是 APIPA 假地址

**现象**：`ipconfig getifaddr en0` → `169.254.137.112`。`169.254.0.0/16` 是链路本地地址段，
说明 en0 这块网卡 link up 但没拿到 DHCP 租约。把它写进验证信息是错的。

**解决**：改为「默认路由网卡 → 该网卡地址」，见第 4.3 节。真实出口是 `en1`
（Wi-Fi），地址 `192.168.30.213`，与 `route -n get default` 的
`gateway: 192.168.31.254` 同网段，可交叉验证。

### 5.3 softfloat 从一个叫 `Linux-x86_64-GCC` 的目录里构建

> 本节是**源码级论证，不引用构建日志**：本次 NEMU 构建时 `softfloat.a` 已存在，
> make 跳过了该目标，所以 `p1_nemu_build.log` 里没有 softfloat 相关输出
> （`grep -i softfloat logs/stage1/p1_nemu_build.log` 零命中，可自行复核）。

**源码事实**：`work/NEMU/scripts/softfloat.mk` 把构建目录名写死为 `Linux-x86_64-GCC`：

```make
SOFTFLOAT_BUILD_PATH = $(abspath $(SOFTFLOAT_REPO_PATH)/build/Linux-x86_64-GCC)   # :10
ifeq ($(ISA),riscv64)
SPECIALIZE_TYPE = RISCV                                                           # :17
endif
$(SOFTFLOAT):
	SPECIALIZE_TYPE=$(SPECIALIZE_TYPE) $(SOFTFLOAT_OPTS_OVERRIDE) $(MAKE) -s -C $(SOFTFLOAT_BUILD_PATH) all   # :29
```

该分支由 `CONFIG_FPU_SOFT` 触发（`softfloat.mk:1`），而 kmhv2 的两份配置都打开了它：
`configs/riscv64-xs-kmhv2_defconfig:228`、`configs/riscv64-xs-kmhv2-ref_defconfig:205`
（行号以 `git -C work/NEMU show HEAD:<file>` 的基线版本为准）。
因此在 aarch64 机器上首次构建时，终端会打出带 `Linux-x86_64-GCC` 字样的命令行。

**为什么不是问题**：这只是 berkeley-softfloat-3 上游的目录命名惯例，
该目录下的 Makefile 不含 `-m64` 之类的架构相关参数，纯 C 实现，aarch64 上正常编译链接。
**不是问题，无需修改**，但值得在此记一笔，免得后面有人看到 `x86_64` 字样误判配错了架构。

**同一现象的真实日志旁证**（注意：是另一个仓库的 softfloat，不是 NEMU 的）：
`logs/stage1/p1_t3_yunsuan_sim.log:9` 里 yunsuan 侧首次构建打出了
`SPECIALIZE_TYPE=RISCV  … -C …/yunsuan/resource/softfloat/repo/build/Linux-x86_64-GCC all`，
与上面 `softfloat.mk:29` 的配方逐字对应 —— 两个仓库各自带了一份同源的 `softfloat.mk`。

### 5.4 `docker build` 的 `FromPlatformFlagConstDisallowed` 警告

**现象**（`p1_docker_build.log:5` 与 `:2012`）：

```
FromPlatformFlagConstDisallowed: FROM --platform flag should not use constant value "linux/arm64" (line 16)
```

**结论**：BuildKit 的 lint 提示，不是错误，镜像正常产出。保留 `FROM --platform=linux/arm64`
是**故意的**：本项目明确只要 arm64 镜像，写死比依赖调用方记得传 `--platform` 更不容易出错。
脚本里同时也传了 `--platform linux/arm64`，双保险。
（后续为支持 Linux x86_64 已改为不写死：`Dockerfile.xsdev` 不再带 `FROM --platform`，平台由
`scripts/01_setup_env_docker.sh` 按宿主架构传入 `linux/amd64` 或 `linux/arm64`，因此该提示不会再出现。）

### 5.5 链接器 `LOAD segment with RWX permissions` 警告

**现象**（`p1_hello_xiangshan.log:27`）：裸机程序把 `.text/.rodata/.data/.bss` 放在同一个
可读可写可执行段里，ld 2.42 会提醒。

**结论**：裸机程序本来就没有 MMU 保护的概念，NEMU 也是按扁平 bin 直接装载，
该警告不影响正确性。未做处理。

### 5.6 NEMU Makefile 里的 `git_commit` 会不会污染上游仓库

**排查**：`NEMU/Makefile:156-158`、`:172`、`:176` 在 `compile` / `run` / `gdb` 时会 `$(call git_commit, ...)`，
而 `scripts/git.mk` 里的实现是 `git add $(NEMU_HOME)/.. -A` + `git commit`，
听起来会往上游仓库里提交东西（违反 MASTER_PLAN 执行纪律第 5 条）。

**结论**：`scripts/git.mk:9` 的 `define git_commit` 被 `ifdef __NOT_DEFINED` 包住，
默认不定义，`$(call git_commit, ...)` 展开为空，**不会产生任何提交**。
构建后实测 `git -C work/NEMU status --short` 输出为空、`git log -1` 仍是 `9090839`，证实无污染。

## 6. 局限性

### 6.1 本阶段的验证信息跑在 NEMU 上，不是香山全核 RTL

**必须明确写明**：第 4 节的 `hello xiangshan, ...` 由 **NEMU（riscv64-xs-kmhv2 配置的指令集模拟器）**
执行产生，**不是**由香山 RTL 的 Verilator 全核仿真产生。NEMU 是香山官方的 difftest 参考模型，
对架构可见状态（通用寄存器、向量寄存器、CSR、内存）与香山逐指令一致，但它**不建模微架构**：
没有流水线、没有发射队列、没有 cache 时序。因此本层验证能回答"指令语义对不对"，
不能回答"几个周期、怎么拆 uop"——后者由硬件侧的 L0/L1 层（YunSuan 功能单元 Verilator 仿真 + 波形）回答。

### 6.2 全核香山仿真在本机不可行 —— 实测结论

完整调查过程与原始命令输出在 `logs/stage1/p1_fullcore_feasibility.log`（290 行）。摘要：

| 待验证的说法 | 实测结论 | 证据位置 |
|---|---|---|
| 官方镜像 `ghcr.io/openxiangshan/xs-env` 只有 amd64 | **成立**。manifest list 里只有一个 `linux/amd64` 镜像 manifest，另一个 `unknown/unknown` 条目是 OCI 构建证明(attestation)，不是可运行镜像；无 arm64 条目。该 amd64 镜像压缩后 20 层共 1.04 GiB | `p1_fullcore_feasibility.log:14-60` |
| 但 amd64-only 是否就等于跑不了 | **否**。本机 Docker 可以模拟运行 amd64：`docker run --platform linux/amd64 ubuntu:24.04` 正常启动，容器内 `uname -m` = `x86_64` | `:88-102` |
| 模拟有多慢 | 纯整数 bash 算术循环 400k 次：arm64 `0.575s` vs amd64 `0.969s`，约 **1.7×**；`sha256sum` 400 MiB：`0.231s` vs `0.935s`，约 4.0×（后者偏高，因为 arm64 侧用到了 SHA-2 硬件扩展，不公允）。以 1.7× 为准 | `:104-168` |
| 模拟后端是 Rosetta 还是 qemu-user | **未能直接取证**。容器内看不到 `/run/rosetta`，也没有可观察的 `binfmt_misc` 挂载点。1.7× 的量级明显优于 qemu-user 典型的 10× 以上，更像 Rosetta，但这是推断不是证据，如实标注 | `:206-213` |
| 真正的阻塞是什么 | **内存**。香山官方 `Makefile` 默认 `JVM_XMX ?= 40G`（`work/XiangShan-kmhv2/Makefile:81`，kunminghu-v2 与 v3 一致）；官方 release CI 即使压到 `JVM_XMX=10g` 也要额外 `fallocate` 32 GiB swap（`work/XiangShan(kunminghu-v3)/.github/workflows/release.yml:175,189`；注意 v2 分支的 `release.yml` 只有 93 行、不含该步骤，这里引 v3 作为官方资源需求的旁证，路径见 `p1_fullcore_feasibility.log:193-195` 的 grep 命令与输出）。本机 Docker Linux VM 总内存 `8217575424 B = 7.65 GiB`（宿主物理内存 16 GiB），连降配后的 10 g 堆都放不下 | `:179-204` |
| gsim 能否替代 Verilator | **部分能**。`OpenXiangShan/gsim` 最新 release（`master-2026-10-13-91c79cd`）提供 `gsim-clang19.1.7-ARM64` / `gsim-clang21.1.8-ARM64` 预编译二进制，URL 返回 HTTP 200；官方 `xs-env/install-scripts/gsim.sh:22` 本来就把 aarch64 映射到 ARM64 资产。但 gsim 替代的是"Verilog → 可执行仿真器"这一步，**前一步**的 mill/Chisel 全核精化（吃 JVM 堆那一步）照做不误，内存门槛不变 | `:169-178`、`:214-233` |

**最终判定**：全核 XiangShan RTL 仿真（含全核 difftest）在本机**不可行，本阶段未执行**。
按既定要求，**没有真的去跑 40 GB 堆的全核构建**，上述判定来自"官方公开的资源要求 + 本机实测资源
与模拟能力"的对照，不是一次失败构建的事后解释。

若后续确需全核：需要一台 ≥64 GiB 内存的 x86_64 Linux 机器，直接用官方
`ghcr.io/openxiangshan/xs-env` 镜像。本机的 amd64 模拟能力只解决"架构"问题，解决不了"内存"问题。

> **后续补充（阶段三）**：全核 difftest 之后在一台 Ubuntu 22.04 x86_64 服务器（128 核、约 1 TB 内存）上原生完成（未用 xs-env 镜像），见 `docs/stage3/23_全核difftest验证报告.md`。实测 MinimalConfig 构建中 Verilator 前端峰值 RSS 59.2 GB、mill 精化 JVM 峰值 20.4 GB（`logs/stage3/fullcore/build_time_breakdown.log:13,39`），印证了本节「内存是真正阻塞」的判断；另需 clang++（`23` §3.3）。本节结论作为阶段一的记录保留。

### 6.3 其他如实标注

- `work/NEMU/resource/` 下四个第三方仓库由上游 Makefile 在 make 解析阶段自动浅克隆，
  **没有固定 tag**，复现时拿到的 commit 可能与 `docs/stage1/00_环境版本锁定.md` N3 节记录的不同。
  其中只有 berkeley-softfloat-3 会被真正编译进 NEMU 二进制。
- 镜像里没有 JDK / mill / Verilator / gsim，因此**不能**在这个容器里做 RTL 精化或 Verilator 仿真；
  那部分由硬件侧在宿主机原生环境完成。
- 本阶段只验证了 NEMU 能执行 RVV 1.0 的 `vadd.vv`，**尚未**涉及 vdot 指令扩展（P5 的内容）。
