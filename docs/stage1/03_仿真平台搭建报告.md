## 4. 平台架构

### 4.1 VLEN=128 的确认

两侧都硬编码为 128，且互相对应：

* Chisel 侧：`yunsuan/src/test/scala/top/VectorSimTop.scala:14`
  ```scala
  trait VSPParameter {
    val VLEN       : Int = 128
    val XLEN       : Int = 64
  ```
* C++ 侧：`yunsuan/src/test/csrc/include/vpu_constant.h:13`
  ```c
  #define VLEN 128
  #define XLEN 64
  ```
* 功能单元内部：`yunsuan/src/main/scala/yunsuan/vector/VectorALU/VIFuParameters.scala:4` 的
  `VIFuParam.VLEN = 128`，`VIFuInput.vs1/vs2/old_vd/mask` 均为 `UInt(128.W)`
  （`VAluBundles.scala:88-96`）。

因此**无需额外配置**，L1 平台天然就是 VLEN=128。

## 5. 遇到的真实问题与修复

### 5.1 `espresso` 是 Linux x86-64 二进制，macOS/arm64 执行失败

**现象**（`p1_t3_yunsuan_sim.log:14-24`）：

```
/.../yunsuan/src/main/resources/espresso: /.../espresso: cannot execute binary file
Exception in thread "main" os.SubprocessException: Result of espresso: 126
  at chisel3.util.experimental.decode.EspressoMinimizer$.espresso(EspressoMinimizer.scala:82)
  ...
  at yunsuan.vector.VectorConvert.VectorCvt.<init>(Convert.scala:30)
```

**根因**：`yunsuan/src/main/resources/espresso` 是
`ELF 64-bit LSB pie executable, x86-64 ... for GNU/Linux 3.2.0`。
`yunsuan/build.sc` 把该 resources 目录追加到 forked JVM 的 PATH（`build.sc` 的 `envPATH`），
Chisel 的 `decoder` 在做译码表最小化时会 `os.proc("espresso")` 调它。
Chisel 只捕获"找不到 espresso"（`EspressoNotFoundException`）并回退到 QMC；
"找到了但执行失败（exit 126）"不在捕获范围内，于是直接中止精化。

**修复**：从源码构建 arm64 原生 espresso，并放在 PATH **前部**（resources 目录是追加在末尾的，前部优先）。

```bash
git clone --depth=1 https://github.com/classabbyamp/espresso-logic work/tools/espresso-logic
make -C work/tools/espresso-logic/espresso-src
cp work/tools/espresso-logic/bin/espresso work/tools/bin/espresso
file work/tools/bin/espresso   # Mach-O 64-bit executable arm64
```

已固化进 `scripts/00_setup_env_host.sh` 第 3 步。

### 5.2 改了 PATH 却不生效 —— mill 缓存了 `forkEnv`

**现象**：装好原生 espresso、`which espresso` 已指向它，`make emu` **仍然**报同样的 126
（`p1_t3_yunsuan_sim.log:112-116`、`214-217`，连续两次）。

**根因**：`yunsuan/build.sc` 里

```scala
val envPATH = sys.env("PATH") + ":" + resourcesPATH

实测缓存文件内容确实是旧 PATH。

**修复**：

```

`scripts/10_build_yunsuan_sim.sh` 在执行前会先 `source scripts/env_host.sh`，
从干净环境开始就不会踩这个坑；若手工改过 PATH，记得删这个缓存文件。

### 5.4 预期会出问题但实际没有的点（记录以免下一位同学重复排查）

* **softfloat 的 `build/Linux-x86_64-GCC`**：`yunsuan/Makefile.softfloat` 硬编码了这个构建目录名，

  `-ldl` 在 macOS 上有 tbd 存根，链接只给出 `ld: warning: ignoring duplicate libraries: '-lpthread'`。**无需修改**。
* **firtool**：Chisel 6.7.0 通过 firtool-resolver 自动下载
  `org.chipsalliance:llvm-firtool:1.62.1`，**有 macOS-arm64 原生二进制**，开箱即用，
  不需要手工装 CIRCT。

## 6. 波形

### 6.1 怎么抓

1. 必须用 `EMU_TRACE=1` 重新构建（Makefile 会给 verilator 加 `--trace`）。
   由于 Makefile 的依赖关系里不含这个开关，**切换时必须先删 `build/emu-compile`**：
   ```bash
   rm -rf build/emu-compile build/emu
   make emu EMU_TRACE=1
   ```
2. 运行时加 `--dump-wave`，并用 `-b/-e` 限定 dump 的周期窗口：
   ```bash
   YS_FUTYPE=5 YS_FUOPTYPE=0 ./build/emu --dump-wave -b 0 -e 120 -O 8 -s 2
   ```
   **坑**：`emu.cpp` 的 `Emulator::reset_ncycles()` 在 `VM_TRACE==1` 时
   **无条件**调用 `tfp->dump()`（`emu.cpp:158-172`，没有 `if (args.enable_waveform)` 保护）。
   所以带 trace 编译出来的 emu **必须始终带 `--dump-wave` 运行**，否则会用未初始化指针崩溃。
   日常回归请用不带 trace 的版本。
3. `-b/-e` 的默认值是 `(uint64_t)-1`，即**不给 `-b/-e` 就什么都不会 dump**（文件只有头部）。
4. 文件名由 `Emulator::waveform_filename()` 生成：
   `build/<YYYY-MM-DD@HH:MM:SS>_dump_wave_seed_<seed>.vcd`。
5. 发生 BADTRAP 时，emu 会自动**重放最后一条激励**并产生
   `*_re_execute_seed_*.vcd`（`emu.cpp:205-230`），同时打印 golden model 的逐元素 trace，
   这是调试失配的首选手段。

按 e64 逐元素相加：`0x000041a710d63af1 + 0x4431b7821c06dac8 = 0x4431f9292cdd15b9` ✓，
高 64 位同理 ✓。按 e8 / e16 切分则**不**匹配 —— 说明 RTL 确实按 `sew` 信号指示的 e64 做加法。
第二笔事务 `sew=1(e16)` 时只有 e16 切分匹配，e32/e64 不匹配，交叉验证成立。

从 `vaddvv_vialufwrapper_fuType5_seed2.vcd` 的第一笔事务（时刻 #25）可以直接看到掩码与 tail 行为：

```
fuType=5 fuOpType=0 sew=2(e32) vstart=0 vl=1 vlmul=0 vm=0 ta=0 ma=1
vs1    = 416f59b3756a1854_0000834e21ac75e2

mask   = 0dafa966079a6e8f_54ba251908d9b7c4

```

* 元素 0：`vm=0`（掩码有效），`mask` 的 bit0 = 0 → 该元素被屏蔽；`ma=1`（mask agnostic）→ 写全 1 `0xffffffff` ✓
* 元素 1…3：`vl=1`，属于 tail；`ta=0`（tail undisturbed）→ 原样保留 `old_vd` 的对应元素 ✓

`vs1 e16[1]=0x589e + vs2 e16[1]=0x6a7e = 0xc31c` ✓，
元素 ≥ vl 全部为 `ffff`（tail agnostic）✓。

> 这段验算的脚本化做法：VCD 的顶层 IO 标识符很短（`B&!`=`io_in_valid`、`A&!`=`io_in_ready`、
> `S&!`=`fuType`、`U&!`=`sew`、`C&!/E&!`=`src_0_0/1`、`G&!/I&!`=`src_1_0/1`、
> `e&!/g&!`=`result_0/1`），可直接 grep。

## 7. XiangShan 全仓 mill 精化的情况

按 T2 的优先级，本阶段选择 **只用 yunsuan 独立 mill 工程**，理由：

1. `yunsuan/` 自带 `build.sc`、`.mill-version`、`Makefile` 和 CI，是一个**完全独立**的 mill 工程，
   不依赖 rocket-chip / utility / difftest，编译只需 80 个 Scala 源文件（实测约 1 分钟）。
2. 本阶段要交付的 VIAlu / VIMac Verilog 和 L1 仿真平台**全部在 yunsuan 内**，
   精化整个 SoC 对本任务没有额外收益。
3. XiangShan 根仓库 `build.sc` 依赖 `ChiselAIA`、`ChiselIOPMP`、`coupledL2`、`fudian`、
   `huancun`、`openLLC` 六个子模块（`build.sc:145/155/177/203/209/229`），
   且用 Ammonite 的 `$file.huancun.common` 导入 `huancun/common.sc`；
   这些子模块在初始状态下**未检出**，build.sc 连解析都会失败（已在 §7.1 补齐并跑通）。
4. XiangShan 官方对全核 Verilator 构建要求约 40 GB JVM 堆，本机 16 GB 内存不具备条件
   （`MASTER_PLAN.md` D3 已记录该约束）。

但为了给 P3 铺路，仍然把"全仓 Scala 编译"这一步跑通了，见下。

## 8. 局限性（必须如实知悉）

### 8.1 上游 CI 的 `make test` 在本机**不通过** —— chiseltest 6.0.0 与 Verilator 5.052 不兼容

`make test`（即 `mill YunSuan.test.test`）的 11 个 ScalaTest 用例**全部失败**
（`p1_t3_yunsuan_sim.log:13841` 起）。根因不是 macOS，而是版本不兼容：

```
../SlideUpLookupModule-harness.cpp:194:5: error: unknown type name 'WData'
  194 |     WData* data = nullptr;
```

chiseltest 6.0.0 生成的 Verilator harness 模板里用了裸类型 `WData`，
而 Verilator 5.052 的头文件已不再提供它（只保留 `WDataInP` / `WDataOutP`）。
失败的用例列表见日志末尾（`VFloatAdderTest`、`VIntDividerTest`、`VCompressTest`、
`VSlide1UpTest`、`VSlide1DownTest` 等共 11 个）。

**影响评估**：这些用例只是 `dut.clock.step(10)` 的**语法冒烟测试**，不做任何功能检查。
真正承载功能验证的是 `make emu` + `./build/emu` 这条链路，它完全正常。
因此**不阻塞** P4 的功能测试工作。

**如果以后确实需要它**：装 Verilator 5.0xx 早期版本（chiseltest 6.0.0 同期），
或把 chiseltest 升级到支持新版 Verilator 的版本（会牵动 build.sc 的依赖版本）。
本阶段**未执行**这两条路径，原因是性价比低且会动上游依赖版本。

### 8.2 VIMac 没有接进 L1 平台，也没有 C++ 参考模型

* `SimTop` 的 fuType 表里没有 VIMac（`VectorSimTop.scala:26-37`）；
* `src/test/csrc/golden_model/` 里没有 `vector_integer_mac.cpp`；
* `vpu_constant.h` 的 `ALL_FUTYPES` 里也没有它。

能做的只有 L0（生成 `VIMac.sv`，已完成）。想在 L1 上测乘法阵列，必须自己接（见 §9）。
`src/test/scala/vector/VectorALU/VIMacSpec.scala` 和 `VIMac64bSpec.scala` 走的是 chiseltest 路径，
受 §8.1 影响同样跑不起来。

### 8.3 `VIntegerALUV2`（VIAluFWrapper）不在上游默认随机测试范围内

`vpu_constant.h:31`：

```c
#define ALL_FUTYPES {VFloatFMA,VFloatDivider,VIntegerALU,VPermutation,VIntegerDivider,VFloatCvt,FloatCvtF2X,FloatCvtI2F}
```

`VIntegerALUV2`（=5）和 `VFloatAdder`（=0）被上游从随机列表里去掉了（上一行被注释的版本里有）。
本报告中 fuType=5 的 10000 组 PASS 是用 `YS_FUTYPE=5` **显式打开**跑出来的，
不是上游默认 CI 覆盖的范围。上游为什么注释掉没有说明，本机实测 `vadd.vv` 这一条是通过的，
但**不代表 VIAluF 的全部 65 个 optype 都通过** —— 本阶段只定向测了 `VADD_VV`。

### 8.4 测试激励的覆盖范围

`./build/emu -O N` 是**纯随机**激励。本阶段跑的是 `vl`/`vlmul`/`vm`/`ta`/`ma` 随机、
`vstart` 恒为 0（`test_driver.cpp:240`，算术指令的 vstart 一律置 0）的组合。
**定向边界用例（±127/−128、全 0、vl=0/1、vstart≠0）属于 P4 的工作，本阶段未做。**

另外 `gen_random_sew()`（`test_driver.cpp:146-157`）对 fuType=5 走 `default` 分支，
返回 `(rand()%3)+1`，即 **sew 只会取 1/2/3（e16/e32/e64），取不到 e8**。
`vdot.vv` 要求 sew=e8，下一位同学加 vdot 时必须改这里。

### 8.5 波形只覆盖功能单元级，不覆盖全核

L1 平台的 DUT 是 `SimTop`，里面只有裸的功能单元加一个握手壳。
**译码、uop 拆分、发射、旁路、写回这些全核行为在 L1 波形里看不到**，
阶段一要求的 `vadd.vv` 全流程分析（译码→拆分→发射→执行→写回）
中"执行"这一段可以用本报告的波形坐实，其余环节必须靠源码分析或其它层级补齐。

* **未执行**：XiangShan 全核 Verilator 仿真（`make emu` 顶层）—— 内存不足，见 §7。
* **未执行**：Docker 方案 —— 原生 macOS 构建已成功，没有必要。

## 9. 下一位同学：怎么往这个平台上加一个新功能单元（vdot）

按依赖顺序，需要改 **6 个地方**（Chisel 3 处、C++ 3 处），缺一不可。

### 9.1 Chisel 侧

1. **实现 FU 本体**
   放在 `yunsuan/src/main/scala/yunsuan/vector/`，建议复用
   `vectorIMAC/VIMac64b.scala`（8×8 乘法阵列已在里面）和
   `VectorALU/VIntAdder64b.scala`（加法树）。
   IO 建议直接用现成的 `VIFuInput` / `VIFuOutput`（`VectorALU/VAluBundles.scala:85-100`），
   它们已经是 VLEN=128 且带 `VIFuInfo`（vm/ma/ta/vlmul/vl/vstart/uopIdx/vxrm）。

2. **登记 fuType**
   `yunsuan/src/test/scala/top/VectorSimTop.scala:26-43` 的 `object VPUTestFuType`
   加一行 `def vdot = "b0000_1010".U(8.W)`（下一个空闲值是 10），
   并把 `unknown()` 的阈值从 `> 9.U` 改成 `> 10.U`（`:40`）。

3. **接进 SimTop**
   * 在 `VSPParameter`（`:13-24`）加 `val VDOT_latency: Int = N`；
   * 在延迟查找表（`:104-115`）加 `VPUTestFuType.vdot -> VDOT_latency.U`；
   * 实例化模块并连线（参考 `viaf` 的写法，`:332-350`），
     产生一个 `vdot_result : VSTOutputIO`；
   * 在结果仲裁表（`:385-396`）加 `VPUTestFuType.vdot -> vdot_result`。

   如果是归约型指令（`vdot.vv` 的结果只写 `vd.u32[0]`），
   注意 `VSTOutputIO.result` 是 `Vec(2, UInt(64.W))`，
   高 64 位要按 `vta` 填 tail（参考 `Reduction.scala` 的做法）。

### 9.2 C++ 侧

4. **登记常量**
   `yunsuan/src/test/csrc/include/vpu_constant.h`：
   * `#define VDot (10)`（接 `vpu_constant.h:27` 之后）
   * 把它加进 `ALL_FUTYPES`（`:31`）才会被随机测试覆盖
   * 定义 opcode 宏与 `VDOT_ALL_OPTYPES` / `VDOT_NUM`（参考 `VIAF_*`，`vpu_constant.h:56-128`）

5. **写 golden model**
   新建 `yunsuan/src/test/csrc/golden_model/vector_dot.cpp`，
   在 `include/gm_common.h` 里声明一个 `class VGMDot : public VGMBase`（参考 `VGMIntegerALUF`，
   实现在 `golden_model/vector_integer_aluF.cpp`，只有 164 行，是最好的模板）。
   `gm_common.cpp` 已经把 vl / vstart / vm / ta / ma 的逐元素处理做成公共逻辑，优先复用。
   > **P6 协同仿真的要求**：这个参考模型最终要换成 NEMU 里**真实的 vdot C 实现**，
   > 所以从一开始就把它写成"薄壳 + 调用一个独立的 .c 函数"的结构，后面换起来成本最低。

6. **接进 TestDriver**
   `yunsuan/src/test/csrc/test_driver.cpp`：
