## 0. 这份交付物解决什么问题

RTL（Chisel/Verilator）、NEMU、协同仿真三条线会各自实现一遍 vdot 的语义。
**只要有两处实现，就会有两套语义**，差分测试就会退化成"互相迁就"。
因此本阶段先把语义固化成一份 C 代码，并让所有下游层级都从它派生：

```
                       tests/golden/vdot_ref.c        ← 唯一的语义实现
                                 │
          ┌──────────────────────┼───────────────────────────┐
          │                      │                           │
  tests/golden/vdot_cli   tests/golden/test_golden   （RTL 侧 C++ 测试平台 /
   （批处理外壳）           （宿主端自检）              NEMU 侧 EHelper 直接引用）
          │
  tests/vectors/gen_vectors.py  ——— 只造激励，期望值全部回调 vdot_cli
          │
  tests/vectors/*.txt  ← 共享语料，Verilator FU 测试平台与 NEMU 测试程序共用
```

与之**独立**的第二份实现放在 `bench/baseline/baseline_ref.c`：它是一台微型
RVV 解释器，按 RVV 1.0 标准指令的语义逐条仿真，再按 `baseline_rvv.S` 的指令
顺序拼出同样的功能。两份独立实现在 25916 组用例上逐位一致，才是正确性证据。

## 1. 寄存器布局与字节序约定（所有下游必须遵守）

VLEN = 128，LMUL = 1，一个向量寄存器 = 16 字节，在 C 中表示为

```c
typedef struct { uint8_t v[16]; } vreg128_t;
```

| 项目 | 约定 | 依据 |
|---|---|---|
| 元素到字节的映射 | element *i*（EEW 位）占 `v[i*EEW/8 .. (i+1)*EEW/8-1]` | RVV v1.0 §4「Mapping of Vector Elements to Vector Register State」 |
| 元素内部字节序 | **小端**：最低有效字节在最低字节下标 | 同上 |
| EEW=8 | `element i == v[i]`，i = 0..15 | |
| EEW=32 | `element i == v[4i] | v[4i+1]<<8 | v[4i+2]<<16 | v[4i+3]<<24` | |
| 掩码寄存器 v0 | `mask bit i == (v0.v[i/8] >> (i%8)) & 1` | RVV v1.0 §4.5「Mask Register Layout」 |
| 文本十六进制 | 32 个小写十六进制字符，**`v[0]` 在最左**（字符 0..1 = `v[0]`，字符 30..31 = `v[15]`） | 本项目约定 |

> ⚠ **最容易踩的坑**：文本十六进制是**字节序**而不是"把寄存器当成一个 128 位
> 大整数打印"。二者恰好相反。请一律使用 `vdot_hex_parse()` / `vdot_hex_format()`，
> 不要自己写 `strtoull`。

验证样例（可在 `tests/vectors/boundary.txt` 中逐条核对）：

| 含义 | 十六进制字符串 |
|---|---|
| EEW=8，element0 = 0x80，其余 0 | `80000000000000000000000000000000` |
| EEW=32，element0 = 0x00040000（262144），其余 0 | `00000400000000000000000000000000` |
| EEW=32，element0 = 0x00040000，element1..3 = 全 1（vta=1） | `00000400ffffffffffffffffffffffff` |

选择"`v[0]` 在最左"的理由：手工编写边界用例时，"第 0 个元素是 0x80"直接写成
以 `80` 开头的字符串，不必在脑子里做一次 128 位反转；而且 C/C++ 侧解析就是
一个 16 次迭代的 `for`，不需要 128 位整数类型。

## 2. 语义规范表（含 RVV 1.0 条文引用）

规范基准：*RISC-V "V" Vector Extension*，**Version 1.0（frozen for public review）**，
文件 `v-spec.adoc`（仓库 `riscv/riscv-v-spec`，tag `v1.0`）。下文的 §号即该文档的
章节号。`Zvdot4a8i` 草案引用见 `docs/_recon/vdot-semantics-research.md` §3。

### 2.1 `vdot.vv vd, vs2, vs1, vm` —— SEW=8，四倍宽全向量归约

```
vd.u32[0] = Σ_{i ∈ active} sext32(vs2.i8[i]) × sext32(vs1.i8[i])
```

| # | 条件 | 行为 | 规范依据 |
|---|---|---|---|
| R1 | `vtype.vsew != 8` | Illegal Instruction（模型返回 `ERR_SEW`，不写 vd） | D2 生效条件；§3.4.1 |
| R2 | `vstart != 0` | **Illegal Instruction**（返回 `ILLEGAL_VSTART`，不写 vd，不改 vstart） | §14 原文：*Vector reduction operations raise an illegal instruction exception if `vstart` is non-zero.*；§3.7「`vstart` is not modified by vector instructions that raise illegal-instruction exceptions」 |
| R3 | `vstart >= vl`（含 `vl == 0`） | **不写回任何元素，连 tail 也不写** | §5.4：*When `vstart` ≥ `vl` … no elements are updated … including that no tail elements are updated with agnostic values*；§14：*If `vl`=0 … the destination register is not updated* |
| R4 | body 内 `mask(i)==0` 的**源**元素 | 排除出求和 | §14：*Inactive elements from the source vector register group are excluded from the reduction* |
| R5 | 目的元素 0（EEW=32） | `vl != 0` 时**总是写回**，与掩码无关；全部源元素被掩掉时写入 0 | §14：*the scalar operand is always included regardless of the mask values*（本指令的隐含标量初值为 0） |
| R6 | 目的元素 1..3（EEW=32，即字节 4..15） | tail：`vta=1` → 全 1；`vta=0` → 保持不变 | §14：*The other elements in the destination vector register (0 < index < VLEN/SEW) are considered the tail*；§3.4.3 |
| R7 | `vtype.vma` | **对本指令无意义**（归约没有 inactive 的目的元素），模型接受但忽略 | §5.4 inactive 定义仅作用于目的元素 |
| R8 | `vstart > 15` | 超出当前 SEW 的最大元素下标，reserved；模型返回 `ERR_VSTART_RANGE` | §3.7：*The use of `vstart` values greater than the largest element index for the current SEW setting is reserved*（并建议 trap） |
| R9 | 执行结束 | `vstart` 置 0 | §3.7；由 NEMU/RTL 负责，模型不持有 CSR |

**溢出证明（为什么 `vdot.vv` 不需要饱和逻辑）**
单个乘积 `p = sext32(a)·sext32(b)`，`a,b ∈ [-128,+127]`：
`max p = (-128)·(-128) = +16384`，`min p = (-128)·(+127) = -16256`，故 `|p| ≤ 2^14`。
VLMAX = 16，所以 `|Σp| ≤ 16·16384 = 262144 = 2^18 < 2^31-1`。
**结论：`vdot.vv` 的结果恒在 int32 范围内，不可能溢出，不需要饱和，也不置 `vxsat`。**
代码中的实现仍然把累加做在 `uint32_t` 上（`tests/golden/vdot_ref.c:100`、`:165`），
这样即使将来扩到更大 VLEN 也不会触发 C 的有符号溢出 UB。

### 2.2 `vdotacc.vv vd, vs2, vs1, vm` —— 累加变体

规则与 §2.1 **完全相同**，仅 R5 改为：

```
vd.u32[0] = vd.u32[0] + Σ_{i ∈ active} sext32(vs2.i8[i]) × sext32(vs1.i8[i])
```

累加按 2^32 模回绕，不饱和（与 §11「overflows wrap around」一致）。
`vd` 作为第三源读取。注意 R3 仍然成立：`vl=0` 时连读都不发生，`vd` 原样保留。

### 2.3 `vdot4a.vv vd, vs2, vs1, vm` —— SEW=32 分组点积累加

```
∀ i ∈ active: vd.u32[i] += Σ_{j=0}^{3} sext32(vs2.i8[4i+j]) × sext32(vs1.i8[4i+j])
```

这是**逐元素**指令，不是归约。按 RVV 的一般规定 `vstart` 本应正常生效，
但**裁定 S-7'（见 §7）把它也判为非法** —— 这是平台约束，不是规范要求。
VLMAX = 4。

| # | 条件 | 行为 | 规范依据 |
|---|---|---|---|
| Q1 | `vtype.vsew != 32` | Illegal Instruction（`ERR_SEW`） | D2 生效条件；`Zvdot4a8i` draft §「requires SEW==32」 |
| **Q1b** | **`vstart != 0`** | **Illegal Instruction（`ILLEGAL_VSTART`）** | **裁定 S-7'**（§7）。**不是** RVV 的要求，是平台约束优先原则的结果；SKIP 策略下恢复为 Q3 |
| Q2 | `vstart >= vl`（含 `vl == 0`） | 不写回任何元素，连 tail 也不写 | §5.4 |
| Q3 | `i < vstart`（prestart） | 目的元素保持不变（S-7' 之后仅 SKIP 策略可达） | §3.7 / §5.4 |
| Q4 | body & mask=1（active） | 按上式累加，2^32 模回绕 | `Zvdot4a8i` 伪代码；§11 |
| Q5 | body & mask=0（inactive） | `vma=1` → 该 32 位元素写全 1；`vma=0` → 保持不变 | §3.4.3 / §5.4 |
| Q6 | `i >= vl`（tail） | `vta=1` → 写全 1；`vta=0` → 保持不变 | §3.4.3 |
| Q7 | 掩码粒度 | **32 位元素**（每个结果 1 个 mask bit），不是每字节 1 个 | `Zvdot4a8i` draft；与 ARM SDOT / x86 VPDPBUSD 一致 |
| Q8 | `vstart > 3` | reserved，模型返回 `ERR_VSTART_RANGE` | §3.7 |

子元素定位：element *i* 的第 *j* 个 int8 取字节 `4i+j`。`Zvdot4a8i` 规范用 Sail 的
MSB-first 拼接 `{a0@a1@a2@a3}` 书写，但 4 个乘积相加，**字节顺序不影响结果**，
两种写法等价。

### 2.4 状态码一览

| 状态名 | 值 | 含义 | 对 vd 的影响 |
|---|---|---|---|
| `OK` | 0 | 正常执行（含"按规范不写回"的情形） | 按规范 |
| `ILLEGAL_VSTART` | 1 | `vstart != 0`。vdot/vdotacc 依 S-1（RVV §14），vdot4a 依 S-7'（平台约束） | 不变 |
| `ERR_SEW` | 2 | `vtype.vsew` 与指令要求不符 | 不变 |
| `ERR_VL` | 3 | `vl > VLMAX`（架构上不可达，防调用方写错） | 不变 |
| `ERR_VSTART_RANGE` | 4 | `vstart` 超出当前 SEW 的最大元素下标 | 不变 |
| `ERR_ARG` | 5 | 空指针 / `vta`,`vma` 非 0/1 | 不变 |
| `ERR_POLICY` | 6 | 未知 vstart 策略 | 不变 |
| `ERR_OP` | 7 | 未知指令编号 | 不变 |

**没有使用 `assert`**：所有非法配置都通过返回值报告，便于 NEMU 侧把
`ERR_SEW` / `ILLEGAL_VSTART` 直接映射成 `longjmp_exception(EX_II)`。

## 3. 共享语料格式规范

每个 suite 一个纯文本文件，一行一个用例，字段以空白分隔。

### 3.1 字段定义

```
# fields: op vsew vstart vl vm vta vma vs1_hex(32) vs2_hex(32) vd_in_hex(32) vd_expected_hex(32) v0_hex(32) status
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `op` | 字符串 | `vdot` / `vdotacc` / `vdot4a` |
| `vsew` | 十进制 | **元素位宽**（8/16/32/64），不是 `vtype.vsew` 的 3 位编码。换算：`vtype.vsew = log2(vsew/8)` |
| `vstart` | 十进制 | `vstart` CSR |
| `vl` | 十进制 | `vl` CSR |
| `vm` | 0/1 | **指令编码 bit25**：`1` = 不使用掩码；`0` = 用 `v0` 掩码 |
| `vta` | 0/1 | `vtype.vta` |
| `vma` | 0/1 | `vtype.vma` |
| `vs1_hex` | 32 hex | 源寄存器 vs1 |
| `vs2_hex` | 32 hex | 源寄存器 vs2 |
| `vd_in_hex` | 32 hex | 执行前的 vd（`vdotacc`/`vdot4a` 同时是第三源） |
| `vd_expected_hex` | 32 hex | **期望的执行后 vd**（非 OK 状态时恒等于 `vd_in_hex`） |
| `v0_hex` | 32 hex | 掩码寄存器 v0 完整 128 位（`vm=1` 时内容无意义，仍然给出） |
| `status` | 字符串 | §2.4 中的状态名 |

以 `#` 开头的行是注释/元信息，消费端应跳过。文件头部固定包含：

```
# suite: <名字>        # cases: <条数>      # policy: strict|skip
# seed: <RNG 种子>     # vlen: 128          # lmul: 1
# generator: tests/vectors/gen_vectors.py
# oracle: tests/golden/vdot_ref.c (via tests/golden/vdot_cli)
# hex layout: 32 chars per register, v[0] leftmost
# rationale: ...（覆盖理由，可多行）
# fields: ...
```

### 3.2 消费方式

* **C++（Verilator / YunSuan FU 测试平台）**：见 `tests/golden/example_cxx_consumer.cpp`，
  15 行 `std::istringstream` 即可解析；寄存器用 `vdot_hex_parse()` 转成 `uint8_t[16]`，
  可直接按字节灌进 DUT 的 128 位端口。本机已实测该示例跑通 `boundary.txt`
  与 `vdot4a_random.txt` 全部用例。
* **C（NEMU 侧测试程序）**：`sscanf(line, "%31s %u %u %u %u %u %u %63s ...")`，
  同样用 `vdot_hex_parse()`。`test_golden.c:66` 就是现成的实现。
* **关键提醒**：`status != OK` 的用例表示该配置应当**触发 Illegal Instruction**
  （`ILLEGAL_VSTART` / `ERR_SEW`），`vd_expected` 等于 `vd_in`。
  FU 级测试平台若不建模异常，应**跳过**这些用例并在报告中说明。

### 3.3 唯一语义来源的保证方式

1. `gen_vectors.py` 里**没有任何一行点积/掩码/尾部策略代码**。它只构造输入
   （`build_positive` / `build_negative` / `build_boundary` / `build_random`），
   然后把全部用例以文本流一次性管道给 `vdot_cli`，由 C 参考模型算出
   `vd_expected` 和 `status`（`gen_vectors.py` 的 `evaluate()`）。
2. `test_golden.c` 的 **[1] 回环检查**把文件里每一条用例重新喂回参考模型，
   确认文件中记录的期望值与模型现算结果逐位一致 —— 即便有人手工改过语料，
   也会立刻被发现。
3. 若将来需要调整语义，只改 `vdot_ref.c`，然后
   `make -C tests/golden vectors && make -C tests/golden log`，全部语料与日志
   同步刷新，不存在"Python 与 C 漂移"的可能。

## 5. RVV 1.0 基线实现（赛题 3.2）

### 5.1 三个候选序列

全部只用 RVV 1.0 标准指令，已用 `riscv64-elf-gcc 16.2.0 -march=rv64gcv -mabi=lp64d`
实测汇编通过（日志 `[5]` 段），反汇编见 `make -C bench/baseline dis`。

| 候选 | 核心指令 | 循环内向量指令 | 循环内 `vsetvli` | 循环内串行归约 | 寄存器占用 | 结论 |
|---|---|---:|---:|---|---|---|
| **A** | `vwmul.vv`(8→16) + `vwredsum.vs`(16→32) | 6 | 2 | **有** | v1,v2,v4:v5,v8 = 5 | 赛题/总体方案提到的朴素写法；归约在循环内，吞吐最差 |
| **B** | `vsext.vf4`×2 + `vmacc.vv`(32) | 7 | 2 | 无 | v1,v2,v4-v7,v8-v11,v16-v19 = 14 | 指令最多、寄存器压力最大 |
| **D** | `vwmul.vv`(8→16) + `vwadd.wv`(16→32) | **6** | 2 | **无** | v1,v2,v4:v5,v8-v11 = 8 | **选定**：指令数与 A 持平，但把串行归约移出循环，是最强的基线 |

**为什么选 D 而不是 A**：如果拿 A 当基线，相当于给自己挑了一个弱对手 ——
A 的瓶颈是 RVV 归约天生串行、在香山上是多拍非流水操作，用它做分母会把
加速比吹上去。D 和 A 的指令条数完全相同（6 条向量），但 D 把归约挪到了循环外，
是一个真正有经验的 RVV 程序员会写出来的版本。**用 D 做基线，结论才站得住。**

**为什么不是 B**：B 同样没有循环内归约，但多 1 条向量指令，且需要三组 EMUL=4
的寄存器组（14 个向量寄存器），在真实 kernel 里会挤掉其它变量。保留 B 是为了
说明"把 int8 先扩到 int32 再 MAC"这条路已经评估过。

**选 D 的一个工程细节（必须写进 RTL/NEMU 测试）**：D 的累加器指令必须用
`tu`（tail undisturbed）。若用 `ta`，最后一次不足 16 个元素的迭代会把
lane[vl..15] 已累加的值写成全 1，结果错误。`baseline_rvv.S` 和
`baseline_intrinsics.c` 都用了 `tu`，`test_golden` 的长向量检查覆盖了
`N ∈ {1,2,3,5,15,17,31,33,63,127,255,1024,4096}` 等非 16 整数倍的情形。

### 5.3 长向量循环（N ≫ 16）

循环体按"每处理 16 个 int8 对"计：

| 实现 | 向量指令 | 标量指令 | `vsetvli` 次数 | 循环内串行归约 | 循环携带依赖 |
|---|---:|---:|---:|---|---|
| 基线 A | 6 | 4 | 2 | **有**（`vwredsum.vs`） | `vwredsum.vs` → 下轮 `vwredsum.vs` |
| 基线 B | 7 | 4 | 2 | 无 | `vmacc.vv` → 下轮 `vmacc.vv` |
| **基线 D（选定）** | **6** | 4 | 2 | 无 | `vwadd.wv` → 下轮 `vwadd.wv`（一次宽加法） |
| **vdot（`vdotacc.vv`）** | **4** | 4 | **1** | 无 | `vdotacc.vv` → 下轮 `vdotacc.vv`（整条乘法阵列+加法树） |
| **vdot4a（`vdot4a.vv`）** | **4** | 5 | **1** | 无 | `vdot4a.vv` → 下轮 `vdot4a.vv`（加法树只有 3 级） |

按 N = 4096（256 次迭代）展开：

| 实现 | 向量指令总数 | 全部指令总数 | 相对基线 D 的向量指令比 |
|---|---:|---:|---:|
| 基线 A | 1536 | 2560 | 1.00× |
| 基线 B | 1792 | 2816 | 0.86× |
| 基线 D | 1536 | 2560 | 1.00× |
| vdot（vdotacc） | 1024 | 2048 | **1.50×** |
| vdot4a | 1024 | 2304 | **1.50×** |

**诚实的结论与限制**：

1. **指令条数**：向量指令 1.5×、总指令 1.25×。这是可以直接数出来的、不依赖
   任何微架构假设的收益。
2. **`vtype` 切换**：基线每轮要在 e8 与 e16 之间切 2 次，vdot 侧只需 1 次。
   香山上 `vsetvli` 改变 `vtype` 可能引发流水线阻塞，但**具体代价必须由 P7 实测**。
3. **循环携带依赖是把双刃剑**：vdot 版把 16 次 MAC 压进一条指令，循环携带
   依赖链因此变成"整条乘法阵列 + 加法树"的延迟；基线 D 的循环携带依赖只是
   一次宽加法。**在未展开的循环里，vdot 不一定更快。**
   正确的用法是用多累加器展开（`v8/v9/v10/v11` 轮转），
   `baseline_intrinsics.c:baseline_dot_i8_seqD_unroll4_intr` 给出了基线侧的
   4 路展开对照组，P7 必须对两边都做展开后再比较，否则结论不成立。
4. `vdot4a` 的 4 条 lane 累加器彼此独立、加法树只有 3 级（vs. DOTR 的 4 级），
   循环携带依赖链比 `vdotacc` 更短，是长向量场景下更优的形态。
5. 本节**没有**任何周期数、IPC 或加速比数字 —— 那些必须来自 P7 的实测。

### 5.4 intrinsics 版与手写汇编的差异（实测）

`riscv64-elf-gcc 16.2.0 -O2` 把 `baseline_dot_i8_seqD_intr` 的循环体编译成
**7 条向量指令**，比手写汇编多一条 `vmv4r.v v8,v4`（`_tu` 形式的 intrinsic
强制产生了一次寄存器组拷贝）。反汇编证据可用
`make -C bench/baseline dis` 复现。做性能对比时应以手写汇编版为准，
并在报告中注明编译器这一条额外开销。

## 7. 语义裁定记录

> D2 给出了三条指令的核心公式，但 `vstart`/`vma`/tail 粒度等细节存在多种可
> 辩护的读法。以下逐条列出分歧、所选方案与理由。**没有任何一条是默默选的。**

### 裁定的修订历史

本记录**不删除被推翻的裁定**，而是保留原文并标注修订，理由有二：
一是评审需要看到判断是怎么演进的；二是「为什么会判错」本身就是结论的一部分。

| 裁定 | 状态 | 提出阶段 | 修订阶段 | 触发者 |
|---|---|---|---|---|
| S-1 ~ S-6、S-8、S-9 | 有效，未修订 | P3 参考模型 | — | — |
| **S-7**（vstart 部分） | **已被 S-7' 取代** | P3 参考模型 | P6 协同仿真 | **NEMU ↔ RTL 协同仿真** |
| S-7（`4i+j` 子字节索引部分） | 有效，未修订 | P3 参考模型 | — | — |
| **S-7'** | 有效 | **P6 协同仿真** | — | — |

**一句话总结**：S-7 是在只看 RVV 规范、只看自己的参考模型时做出的裁定，它在
*规范层面*站得住，却**比目标微架构允许的更宽**。这个错误无法由「自写黄金模型对比
自写 RTL」发现 —— 两边都会照 S-7 实现，从而一致地错下去。它只能由
**真 NEMU ↔ 真香山 RTL** 的协同仿真发现，而且是在 1946 条激励上确定性地暴露出来。
详见 S-7' 与 `docs/stage3/21_协同仿真验证报告.md` §7.3。

### S-1 归约指令遇到 `vstart != 0`（最重要的一条）

* **分歧**：`docs/_recon/vdot-semantics-research.md` §7.4 建议"支持任意 vstart"
  （按 prestart 规则跳过 `i < vstart` 的源元素）；而 RVV 1.0 §14 明文写着
  *Vector reduction operations raise an illegal instruction exception if
  `vstart` is non-zero.*
* **裁定：采用规范字面读法 —— `vdot.vv` / `vdotacc.vv` 在 `vstart != 0` 时
  抛 Illegal Instruction**（模型返回 `ILLEGAL_VSTART`，不写 `vd`）。
* **理由**：
  1. 这是 RVV 1.0 §14 的原文规定，是最不可能被评审质疑的读法；
  2. NEMU 现有的 `reduction_instr()` 正是这样做的 ——
     `work/NEMU/src/isa/riscv64/instr/rvv/vcompute_impl.c:1531` 先调
     `check_vstart_exception()`，该函数在
     `work/NEMU/src/isa/riscv64/instr/rvv/vcommon.c:20-24` 里直接
     `longjmp_exception(EX_II)`。沿用它，NEMU 扩展可以零成本复用现成框架；
  3. **RVV 1.0 基线自己也做不到**：等价基线用的 `vwredsum.vs` 同样是归约指令，
     同样在 `vstart != 0` 时非法。若 vdot 支持而基线不支持，二者就不再是
     "完全相同的功能"，赛题 3.2 的等价性论证会出问题；
  4. 归约天然不可从中途重启（部分和没有架构可见的存放处），禁止非零 `vstart`
     是正确的微架构决策，也让 RTL 省掉一条没人会用的通路。
* **对赛题 2.3.3「vstart≠0」要求的满足方式**：`boundary.txt` 中 `vstart ∈ {1,15}`
  的用例期望行为是"触发 Illegal Instruction 且 `vd` 不变"，这是一个确定的、
  可测的行为，仍然构成有效的边界测试；而 `vdot4a.vv` 是逐元素指令，
  其 `vstart ∈ {1,3}` 的用例是真正的 prestart 数据通路测试。
* **留的后路**：参考模型提供 `VDOT_VSTART_SKIP` 策略（`vdot_*_ex()` 的
  `vstart_policy` 参数）实现放宽读法，并生成了非规范语料
  `tests/vectors/vstart_relaxed.txt`（S-7' 之后扩充为 130 条，含 vdot4a 40 条）。
  若官方语义图或评审要求支持可重启执行，改一个参数重新生成即可，不动任何语义代码。
* **S-7' 之后的补注**：本条中「而 `vdot4a.vv` 是逐元素指令，其 `vstart ∈ {1,3}`
  的用例是真正的 prestart 数据通路测试」一句**已不再适用于规范语料** ——
  S-7' 把 `vdot4a` 的 `vstart != 0` 也判为非法，那些用例的期望值已改为
  Illegal Instruction。prestart 数据通路测试移至非规范语料 `vstart_relaxed.txt`。

### S-2 归约指令的 `vma`

* **分歧**：`vma` 对归约是否有意义。
* **裁定**：**无意义，忽略**。归约只写目的元素 0，而该元素是"标量结果"，
  按 §14 *the scalar operand is always included regardless of the mask values*
  始终写回，不存在 inactive 的目的元素；§5.4 对 inactive 的定义也只作用于
  目的元素。模型接受 `vma` 参数但不使用（`vdot_ref.c` 中有显式 `(void)vma;`）。
* 语料仍然遍历了 `vma ∈ {0,1}`，用于验证 RTL/NEMU **确实忽略**了它。

### S-3 `vdot.vv` 的 tail 以什么 EEW 计

* **分歧**：目的寄存器的 tail 是"元素 1..15（EEW=8）"还是"元素 1..3（EEW=32）"。
* **裁定**：按 **EEW=32**（元素 1..3，即字节 4..15）。理由是与 `vwredsum.vs`
  一致 —— 加宽归约的目的元素宽度是加宽后的宽度，§14 的
  *0 < index < VLEN/SEW* 中的 SEW 指的是结果元素宽度。
* **实际影响为零**：`vta=1` 时两种读法都把字节 4..15 全写 1；`vta=0` 时两种
  读法都保持不变。此处记录只是为了让 RTL 实现者明确写法。

### S-4 全部源元素被掩掉时，`vdot.vv` 写不写 `vd[0]`

* **裁定**：**写，写入 0**（`vdotacc.vv` 写入原值）。依据 §14：标量操作数不受
  掩码影响，始终参与；本指令的隐含标量初值是 0。
* `boundary.txt` 的"all-zero mask"用例即覆盖此情形。

### S-5 `vl = 0` / `vstart >= vl`

* **裁定**：**不写回任何元素，连 tail 都不写**。依据 §5.4
  *When `vstart` ≥ `vl` … including that no tail elements are updated with
  agnostic values*，以及 §14 对 `vl`=0 的专门规定。
* 这与 NEMU `check_vstart_ignore()`
  （`work/NEMU/src/isa/riscv64/instr/rvv/vcommon.c:8-18`）的行为一致。

### S-6 LMUL

* **裁定**：参考模型固定 **LMUL = 1**（VLEN=128，单个寄存器，VLMAX=16 / 4）。
* D2 未规定 LMUL>1 的行为。对 `vdot.vv` 而言 LMUL>1 意味着跨寄存器组归约，
  是一个自然的扩展点但不在赛题要求内；对 `vdot4a.vv` 而言 LMUL>1 是平凡的
  逐元素扩展。**若 RTL 实现了 LMUL>1，必须回来扩展本模型并重新生成语料。**
* 语料文件头的 `# lmul: 1` 即此约束的显式声明。

### S-7 `vdot4a.vv` 子元素的字节顺序，以及 `vstart` 正常生效

> **状态：前半部分（字节顺序）有效；后半部分（`vstart` 正常生效）已被 S-7' 取代。**
> 原文照录，不做删改。

  **结果与顺序无关**，两种写法等价。草案原文也有同样的注记。
* `vdot4a_boundary.txt` 中的 16 组"组 g 子字节 j"单点用例可以直接验证
  RTL 的字节抽取是否接错。
* **裁定（`vstart`，~~原文~~ 已被取代）**：~~`vdot4a.vv` 是逐元素指令而非归约，

### S-7' `vdot4a.vv` 遇到 `vstart != 0`（P6 协同仿真修订，取代 S-7 的 vstart 部分）

* **发现方式**：这一条不是读规范读出来的，是**跑出来的**。P6 的 Level-1 协同仿真
  （真 NEMU `.so` ↔ Verilated 香山译码单元）在 `vdot4a` + `vstart ∈ {1,2,3}` 的
  **1946 条**激励上报出「RTL 判非法 / REF 判合法」的确定性分歧
  （`docs/stage3/21` §7.3，分歧数据来自修订前的快照）。
* **分歧的根因**：两侧都没错，是**ISA 定义比微架构宽**。
  - NEMU 侧按 S-7 刻意不调用 `check_vstart_exception()`；
  - 香山侧 `VecExceptionGen.scala` 的 `vstartIllegal = isVArith && (vstart =/= 0)`
    是**上游 kunminghu-v2 原有的、对所有向量算术指令无条件生效的**判据 ——
    昆明湖 V2 的向量后端根本不支持从非零 `vstart` 恢复执行任何向量算术指令。
* **裁定：`vdot4a.vv` 在 `vstart != 0` 时同样抛 Illegal Instruction**
  （模型返回 `ILLEGAL_VSTART`，不写 `vd`），与 `vdot.vv` / `vdotacc.vv` 一致。
* **理由（平台约束优先原则）**：
  1. **自定义指令的 ISA 语义不应宽于宿主微架构的实际能力。** 本指令是为昆明湖 V2
     定义的自定义扩展，昆明湖 V2 不支持 `vstart` 重启是既有架构事实，不是本项目
     引入的缺陷。让 ISA 向微架构收敛，比为一条自定义指令放宽一条影响**全部**向量
     算术指令的公共判据更合理（后者的回归面是整个向量后端）。
  2. **收敛后三条 vdot 指令的 `vstart` 行为完全一致**，也与同平台上所有标准向量
     算术指令一致。实测对照见 `bench/results/vstart_control.csv`：
     `vadd.vv` / `vwmul.vv` / `vwredsum.vs` / `vmv.s.x` / `vsll.vi` / `vsra.vi` /
     `vmacc.vv` / `vdot4a.vv` 八条指令在 `vstart=1` 时**一律 `TRAP mcause=2`**。
  3. **基线等价性因此更干净**：`vdot4a` 的等价基线用的是 `vsll.vi`/`vsra.vi`/`vmacc.vv`，
     这些逐元素指令在同一平台上同样被 `vstartIllegal` 拦下。S-7 下「vdot4a 能跑、
     基线不能跑」，S-7' 下两者行为一致（`bench/baseline/baseline_ref.c:349`）。
  4. **不修订的代价是确定的**：全核 difftest 一旦跑到 `vdot4a` + `vstart ∈ [1,3]`
     必然 mismatch。这不是理论风险，是协同仿真实测到的 1946 条。
* **影响范围（本次实际改动）**：
  | 文件 | 改动 |
  |---|---|
  | `tests/golden/vdot_ref.c` | `vdot4a_vv_ex()` 增加 `vstart != 0 && policy == STRICT -> ILLEGAL_VSTART` |
  | `tests/vectors/*.txt` | **1545 条** `vdot4a` + `vstart != 0` 用例由 `OK` 翻为 `ILLEGAL_VSTART`（`vdot4a_random` 1539 + `vdot4a_boundary` 6） |
  | `tests/vectors/vstart_relaxed.txt` | 补 40 条 vdot4a prestart 用例（非规范），保住数据通路覆盖 |
  | `work/NEMU` `vdot.c` | `vdot4a_exec()` 增加 `check_vstart_exception(s)` |
  | RTL | **零改动** —— 上游 `vstartIllegal` 已覆盖，由 `tests/unit/vecexcgen_tb.cpp` `[I]` 组实测确认 |
* **可放宽性**：S-7' 是平台约束驱动的决策，**不是指令语义的内在限制**。
  在支持 `vstart` 重启的实现上可以放宽回 S-7：参考模型的 `VDOT_VSTART_SKIP` 策略
  原样保留，`vstart_relaxed.txt` 里 40 条 vdot4a 用例给出了「放宽之后应当是什么行为」
  的可执行定义，且数据通路**本来就正确实现了 prestart**（`Mgu` 的 `info.vstart`
  接的是 `outVecCtrl.vstart`，`VIMacU.scala:140`）。
* **防回退**：协同仿真的故障注入第 5 项（`T3-NEMU-3`）专门删掉 NEMU 里这条检查，
  实测判定分歧立刻从 0 条升到 74 条 —— 也就是说 S-7' 的收敛是被自动化测试守住的，
  不是写在文档里的口头约定（`logs/stage3/cosim/p6_fault_injection.log`）。

### S-8 `funct3` 的选择

* 参考模型**不涉及指令编码**，因此 OPIVV(`000`) 与 OPMVV(`010`) 之争不影响
  本交付物。`bench/baseline/baseline_rvv.S` 的宏按 D2 使用 OPIVV(`000`)，
  并内置编码自校验锚点（期望 `e61101d7` / `ea1101d7` / `ee1101d7`，
  日志 `[5]` 段已实测吻合）。若编码决策变更，只改 `.S` 里的三个宏。

### S-9 `vstart` 超出元素下标范围

* **裁定**：`vstart > VLMAX-1` 时返回 `ERR_VSTART_RANGE`。依据 §3.7
  *The use of `vstart` values greater than the largest element index for the
  current SEW setting is reserved*，并采纳其 NOTE 中"建议实现 trap"的意见。

```bash
cd tests/golden

make clean
```

```bash
cd bench/baseline
make check           # 宿主编译 + riscv64-elf-gcc 汇编/intrinsics 交叉编译
make dis             # 反汇编，核对循环体指令条数与自定义指令编码
```

也写进每个语料文件的 `# seed:` 头。同一份代码在任何机器上重新生成，
字节级一致。种子表：
