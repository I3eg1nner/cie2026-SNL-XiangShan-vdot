## 1. 为什么需要这一层，以及它在分层验证里的位置

`MASTER_PLAN.md` D3 的分层策略里，L3 的定义是「NEMU ↔ RTL 协同仿真：把 NEMU 中**真实的
vdot 实现**作为参考模型逐条比对（非重写的近似模型）」。阶段二（L1）用的参考模型是
`tests/golden/vdot_ref.c`，那是我们自己写的 C 黄金模型；阶段三必须换成**参考模拟器本体**，
否则「NEMU 与 RTL 一致」这句话没有被证明过。

本阶段把 REF 从「C 黄金模型」升级为「真实的 NEMU 共享库」，并且**不是**把语料的期望值
预先算好再比，而是**每条激励都让 NEMU 现场取指、译码、执行一条真实的 vdot 机器指令**，
再把它写出的架构状态与 RTL 的输出逐位比对。语料里的 `vd_expected` 字段在本阶段**被完全
忽略**，只取输入部分作为激励，比对的两端是 NEMU 与 RTL，中间没有第三方。

### 2.1 为什么要跨宿主机 / 容器（历史布局，macOS 建设环境）

NEMU 的 difftest 参考共享库是 **linux/aarch64 ELF**（`logs/stage3/p5_nemu_build.log:143`
`ELF 64-bit LSB shared object, ARM aarch64`；P6 直接复用该 `.so`，`p6_build.log:4-6` 记录了
「已存在且比 vdot.c 新，跳过重建」），必须在 Linux 进程里 `dlopen`；
而 `verilator` 与 `mill` 装在 macOS 宿主机上。因此：
**「mill 精化 + verilator --cc」在宿主机做，「g++ 编译 + dlopen + 运行」在容器里做**。
`verilator` 生成的 C++ 与它的运行时（`verilated.cpp` 等）都是可移植源码，
`scripts/30_run_cosim.sh` 的 `verilate()` 把运行时复制进 `tests/cosim/build/verilator/`
（Docker 只共享仓库目录），再由容器内的 `g++` 一起编译（`p6_build.log:45-50`：容器 `aarch64`、
`g++ 13.3.0`、生成 `ELF 64-bit LSB pie executable, ARM aarch64` 的 `build/cosim`）。

### 2.3 单条激励的锁步流程

`tests/cosim/cosim_main.cpp:172-209` `ref_run()`：

```c
  st.mode = 3;                    // M 模式
  st.mstatus = (2<<34)|(2<<32)|(3<<11)|(1<<13)|(3<<9);   // SXL/UXL=64bit, MPP=M, FS=Init, VS=Dirty
  st.mtvec = 0x80001000; st.pc = 0x80000000; st.satp = 0;
  st.vlenb = 16;
  st.vstart = s.vstart;  st.vl = s.vl;
  st.vtype  = (vma<<7)|(vta<<6)|(sew_code<<3)|vlmul;
  st.vr[0] = v0;  st.vr[vs1] = vs1;  st.vr[vs2] = vs2;  st.vr[vd] = oldVd;

  uint32_t words[2] = {INSTR_FENCE_I, encode_instr(s)};
  ref.mem_to_ref(GUEST_PC, words, sizeof(words));   // difftest_memcpy(..., DIFFTEST_TO_REF)
  ref.regs_to_ref(&st);                             // difftest_regcpy(..., DIFFTEST_TO_REF)
  ref.exec(1);                                      // difftest_exec(1)  -> fence.i
  ref.exec(1);                                      // difftest_exec(1)  -> 被测的 vdot
  ref.regs_from_ref(&st);                           // difftest_regcpy(..., DIFFTEST_TO_DUT)

  out->trapped = (st.pc != GUEST_PC_OP + 4);
```

这正是全核 difftest 在 `Difftest::check_all()` 里做的事情（`difftest.cpp:685` `proxy->sync()`
→ `refproxy.h:252-254` `ref_regcpy(&state.xrf, ...)`；`refproxy.h:369` `ref_exec(1)`），
只是 DUT 侧的状态不是从 ROB 探针来的，而是我们直接组装的激励。

#### 为什么要先执行一条 `fence.i`

这是本阶段踩到的一个**真实坑**，值得写进来：NEMU 的解释器对「已译码指令」按 PC 做缓存
（`work/NEMU/src/cpu/cpu-exec.c:784-793`，`tcache_lookup_instr(cpu.pc)` 命中就直接复用
`Decode` 结构），而 `decode_OP_V` 会把**当时的 `vtype->vsew`** 固化进 `s->v_width`
（`work/NEMU/src/isa/riscv64/instr/rvv/decode.h:39`），`s->vm` 也来自当时的指令字。
本平台在同一个 PC 上反复改写指令和 vtype，第一版实现里 NEMU 始终复用第一条激励的译码结果，
表现为「掩码被忽略 + `vdotacc` 退化成 `vdot`」。

解决办法与真实软件完全一致：**先执行一条 `fence.i`**（`0x0000100F`），它会
`set_sys_state_flag(SYS_STATE_FLUSH_TCACHE)`（`work/NEMU/src/isa/riscv64/instr/rvi/fence.h:22`），
下一次 `execute()` 在循环顶部服务该请求并作废缓存，于是被测指令必定被重新取指译码。
共享库形态下 `cpu_exec()` 断言每次只能走一条指令（`cpu-exec.c:884`
`assert(ref_is_fast() || n <= 1)`），所以拆成两次 `difftest_exec(1)`。

> 这个坑本身就是「协同仿真必须用真实参考模拟器」的一个论据：
> 用自己重写的参考模型永远不会暴露参考模拟器的译码缓存语义。

### 3.2 结构体布局硬校验

`RefRegState`（`tests/cosim/ref_nemu.h:50-85`）逐字段复刻 `riscv64_CPU_state` 的同步窗口
（`work/NEMU/src/isa/riscv64/include/isa-def.h:96-160`），条件编译按
`configs/riscv64-xs-kmhv2-ref_defconfig` 取值（`CONFIG_RVH=y`、`CONFIG_RVV=y`、
`CONFIG_DIFFTEST_CHECK_VCSR/FCSR/SDTRIG=y`、`CONFIG_RV_AME` 未设）。
运行期用 `.so` 导出的 `DIFFTEST_REG_SIZE` 做硬校验，不等就直接退出：

```
[REF] DIFFTEST_REG_SIZE = 1400 B（与本进程 RefRegState 一致）     p6_cosim_run.log:5
```

**1400 B = 256(gpr) + 256(fpr) + 152(基本影子 CSR) + 136(RVH) + 512(vr[32]) + 56(vcsr) + 8(fcsr) + 24(sdtrig)。**
这个数字只有在两边布局完全一致时才会对上；一旦 defconfig 改了，平台立刻报错而不是悄悄算错。

### 7.2 【首轮记录】分歧一：`LMUL != 1` —— 香山当时的快照没有对应的守卫（4469 条）

> **状态：已收敛。** 香山实现树补入 `dotEmulIllegal`（`VecExceptionGen.scala:217`），同步到本工作树后复跑，
> 两组 LMUL 激励 6000/6000 非法一致。以下为首轮原文，未做删改（其中的行号是首轮快照的行号）。


| suite | 分歧 | 明细 |
|---|---:|---|

两组对照把根因钉死了：

* 用 `vd=v1, vs1=v2, vs2=v3` 时，`m2/m4/m8` 之所以也被香山判非法，**纯粹是寄存器组对齐检查
  的副作用**（`VecExceptionGen.scala:276` `regNumIllegal`：LMUL>1 时 `v1`/`v3` 不是合法的
  寄存器组起点）；
* 一旦换成对 LMUL=8 也对齐的 `v8/v16/v24`，香山对 `m2/m4/m8/mf8/mf4/mf2` **一律判合法**，
  而 NEMU 一律判非法 → 3000 条全分歧。

**结论（诚实版）**：在本报告使用的 `work/XiangShan-cosim` 快照上，
**香山的译码侧完全没有实现裁定 S-6（LMUL 固定为 1）对应的非法判定**。
之前看上去"部分一致"是测试向量选择造成的假象。
修复方式很直接 —— 在 `VecExceptionGen.scala` 的 `emulIllegal` 里补一条
`dotLmulIllegal = (dotRedInst || dot4aInst) && (io.vtype.vlmul =/= 0.U)`。
RTL 侧的这条守卫由另一位工程师在 `work/XiangShan-vdot` 上并行补入，**本报告的数据来自
补入之前的快照**，因此记录的是「补入前的真实状态」；补入后把本脚本重跑一遍，
`illegal:lmul!=1(对齐寄存器)` 的 3000 条分歧应当归零。

> 补充：这条分歧**在架构内激励上不可触发**。D2.1 裁定 S-6 明确「本版本固定 LMUL=1」，
> 所有 30000 条架构内随机与 30710 条定向语料（首轮）都是 LMUL=1，它们的值比对 0 失配。
> 分歧只出现在我们**故意构造的越界配置**上。危害是：若软件（或编译器 bug）在 LMUL≠1 时
> 发出 vdot，NEMU 会报非法而香山会静默执行一个未定义行为 —— 在真实全核 difftest 里
> 这会立刻变成一次 mismatch。

### 7.3 【首轮记录】分歧二：`vdot4a` 且 `vstart ∈ {1,2,3}` —— 裁定 S-7 与香山上游约束冲突（1946 条）

> **状态：已收敛，采用下文的「方向 1」，即裁定 S-7'。** 以下为首轮原文，未做删改（其中的行号是首轮快照的行号：
> `VecExceptionGen.scala:294` 的 `vstartIllegal` 在当前实现树为 `:305`、在 pristine 基线为 `:275`；`vdot.c:138-146` 为 S-7' 修订前的 `vdot.c`）。


| suite | 分歧 | 明细 |
|---|---:|---|
| `vdot4a_random.txt` | 1539 | `vstart=1/2/3` 各约 510 条 |
| `illegal:vstart` | 393 | 同上 |
| `vdot4a_boundary.txt` | 6 | 同上 |

根因：

* NEMU 侧按裁定 **S-7**（`vdot4a` 是逐元素指令，`vstart` 正常生效、prestart 元素保持不变）
  **刻意不调用** `check_vstart_exception()`（`vdot.c:138-146` 的注释与代码）；
* 香山侧 `VecExceptionGen.scala:294` 是 **上游 kunminghu-v2 原有的、对所有向量算术指令
  无条件生效的** `vstartIllegal = isVArith && (vstart =/= 0)` —— 昆明湖 V2 的向量后端根本
  不支持从非零 `vstart` 恢复执行任何向量算术指令，一律报非法让软件走慢路径。

也就是说：**这不是 vdot 引入的 bug，而是我们的 ISA 裁定（S-7）比目标微架构允许的更宽。**
两种收敛方向：

1. **改 NEMU 向香山靠**：在 `vdot4a_exec()` 里也调用 `check_vstart_exception()`，
   即把 S-7 收紧成「`vdot4a` 的 `vstart` 必须为 0」。代价是语义上略偏离 RVV 对
   逐元素指令的一般规定，但与昆明湖 V2 的既有行为完全一致，**全核 difftest 直接干净**。
2. **改香山向 NEMU 靠**：给 vdot4a 在 `vstartIllegal` 上开一个例外，并让 `VIMacU` 的
   `Mgu` 正确处理 prestart。代价是动到上游通用逻辑，风险高、收益低。

**本方案的建议是方向 1**，并把它作为 S-7 的修订项记录在案。在修订之前，
真实全核 difftest 一旦跑到 `vdot4a` + `vstart∈[1,3]` 就会报 mismatch —— 这正是本协同仿真
提前发现的价值所在：**如果 REF 用的是我们自己写的黄金模型，这个冲突不会在比对中暴露，
因为黄金模型和 NEMU 实现的是同一套裁定。** 这一冲突本身并非首次被注意到：P6 之前的设计文档
（`git show fe0e6cf~1:docs/stage2/10_vdot指令设计文档.md` 的 `:246` 与 `:1390` 裁定 R-06）已识别出
`vstartIllegal` 会挡掉 `vdot4a` 的 `vstart≠0`，但把它登记为「全核层面不可达」、没有修订 ISA；
协同仿真证明它在全核 difftest 上会确定性地报 mismatch。

### 7.5 方法学结论：为什么 G5b 要靠 NEMU ↔ RTL 协同仿真才被量化并迫使裁定修订

这是本阶段最值得写进结论的一点。

**G5b 不是实现错误，是规范错误。** NEMU 正确实现了 S-7，参考模型正确实现了 S-7，
RTL 的数据通路也正确实现了 S-7 的 prestart 语义（L1 平台上 1545 条 prestart 用例全部逐位通过）。
三方都"对"，错的是 S-7 本身 —— 它比目标微架构昆明湖 V2 允许的行为更宽。

**自写黄金模型对自写 RTL 的验证，在结构上暴露不出这类错误**（下表只比较各验证方式「能否在比对结果中暴露」，
不涉及人工审阅：设计阶段的 R-06 已经靠人工审阅识别出了这一冲突，见下文）：

| 验证方式 | 比较的两端 | 两端的语义来源 | 能否发现 G5b |
|---|---|---|---|
| P3 参考模型自检 | `vdot_ref.c` ↔ `baseline_ref.c` | 同一个人按同一份裁定写的 | **不能**：两端都按 S-7 实现 |
| P4 L1 功能测试 | `VDotTop` / `VIMacU` ↔ `vdot_ref.c` | RTL 与参考模型都按 S-7 | **不能**：FU 级 `vstart` 是自由输入端口，不经过译码；数据通路按 S-7 实现，于是一致地"正确" |
| P5 NEMU 自测 | NEMU `vdot.c` ↔ `vdot_ref.c` 生成的语料 | NEMU 与参考模型都按 S-7 | **不能** |
| **P6 NEMU ↔ RTL 协同仿真** | **NEMU `.so`** ↔ **香山译码单元**（`DecodeUnit` + `VecExceptionGen`，两者都带本项目补丁） | 一端是我们的裁定，**另一端的 `vstartIllegal` 判据是香山团队写的、我们没改过的上游代码** | **能**，而且是 1946 条确定性分歧 |

关键在最后一行：协同仿真的 DUT 不只包含我们写的 vdot 逻辑，还包含**整段上游译码判据**，
而上游的 `vstartIllegal = isVArith && vstart =/= 0` 承载着"昆明湖 V2 不支持 vstart 重启"
这一**平台事实**。我们在写裁定时其实已经注意到它：P6 之前的设计文档 §9 裁定 R-06
（`git show fe0e6cf~1:docs/stage2/10_vdot指令设计文档.md:1390`，以及同版本 `:246` 的处理办法）
写明 `vstartIllegal` 会在译码阶段挡掉 `vdot4a` 的 `vstart≠0`，但结论是「数据通路照 S-7 实现，
接受全核层面不可达」，没有修订 ISA 定义（现行设计文档 `docs/stage2/10_vdot指令设计文档.md:1438`
已把 R-06 标为被 R-17 修订）。也就是说，**风险是设计阶段识别的，协同仿真做的是第一次把它量化成
1946 条确定性分歧**，证明 R-06 的「不可达」判断在全核 difftest 上不成立（REF 执行、DUT 判非法，
必然 mismatch），并由此迫使裁定修订为 S-7'。

一般化的结论是：只有当被比较的两端里至少有一端的语义**不是我们自己写的**，裁定本身的偏差
才有可能在比对结果中暴露，而不必依赖人工审阅时恰好想到、并且对后果判断正确。这是软硬件协同验证
相对于"自己跟自己比"的价值所在，也是本项目把 S-7' 的发现过程完整保留在文档里的原因。

> 推论：G5a（LMUL）最终修的是 RTL。P4 阶段已在实现树补入 `dotEmulIllegal`（`docs/stage2/11_RTL实现说明.md:369`、`:623`），
> 但协同仿真工作树的快照当时尚未同步，于是协同仿真把它定量记录为 4469 条分歧；
> 首轮用 `v1/v2/v3` 时它甚至被寄存器对齐检查部分掩盖（§7.2），换成对齐寄存器才完整暴露。
> 两类分歧都说明：**测试向量的构造必须主动绕开"恰好被别的判据挡住"的情形**。

`Difftest::step()` 每看到一条提交就让 `dlopen` 进来的 NEMU `.so` 执行 `difftest_exec(1)`，

REF/DUT 两个值并终止仿真。

**vdot 相关的两个要点**：

1. 向量寄存器**默认参与比对**。NEMU 侧 `vr[32]` 在 `CONFIG_RVV` 下天然落在
   `DIFFTEST_REG_SIZE` 区间内（`isa-def.h:128-135` / `difftest/ref.c:28`）；
   香山侧只要例化了 `DiffPhyVecRegState` 就会生成 `CONFIG_DIFFTEST_ARCHVECREGSTATE`，
   C++ 侧 `refproxy.cpp:193` 的 `PROXY_COMPARE(vrf)` 随之生效。
   `riscv64-xs-kmhv2-ref_defconfig:218` `CONFIG_DIFFTEST_CHECK_VCSR=y` 让
   `vstart/vl/vtype/vxsat/...` 也进比对（`refproxy.cpp:196`）。
2. **向量指令不支持 skip**：`refproxy.h:274-278`
   ```c
   #ifdef CONFIG_DIFFTEST_ARCHVECREGSTATE
     // TODO: vec skip is not supported at this time.
     if (vecwen) assert(0);
   #endif
   ```
   vdot 不访存、无需 skip，无影响。

## 10. 本方案与全核 difftest 的异同（诚实分析）

### 10.1 相同的部分

| 维度 | 全核 difftest | 本方案 | 等价吗 |
|---|---|---|---|
| REF 是谁 | `dlopen` 的 `riscv64-nemu-interpreter-so` | **同一个 `.so`，同一个 `.o`** | ✅ 完全相同 |
| REF 怎么被驱动 | `difftest_regcpy` / `difftest_memcpy` / `difftest_exec(1)` | **同一套 C API，同样的调用序列** | ✅ 完全相同 |
| REF 执行的是什么 | 真实取指 → 译码 → `exec_vdot_vv` | **同样是真实取指译码执行一条 vdot** | ✅ 完全相同 |
| 比对什么 | `memcmp` 整块 `vrf`（512 B）+ `vcsr` | `vd` 这一个 128 位架构向量寄存器逐位比对 | ⚠️ 本方案只比 `vd`（vdot 唯一的目的寄存器），不比 `vcsr` |
| 比对粒度 | 每提交一条指令比一次 | 每条激励比一次 | ✅ 同为逐指令 |
| 失配怎么办 | `display()` 打印 REF/DUT 并终止 | 打印 REF/DUT 两个 128 位值 + 全部激励参数，计入 FAIL | ✅ 同构 |

### 10.2 本方案覆盖得同样好的部分

* **vdot 数据通路的全部架构可见行为**：16 路 8×8 乘法阵列、可重构折叠加法树、
  符号扩展、32 位回绕、`vdotacc` 的第三源读取、`vdot4a` 的分组累加；
* **`vl` / `vstart` / `vm`(v0 掩码) / `vta` / `vma` 的全部组合**：激励是随机遍历的，
  30000 条架构内随机把 `vl ∈ [0,VLMAX]` × `vm/vta/vma` 的 8 种组合 × 随机操作数都扫过；
* **`vd` 的 prestart / body-active / body-inactive / tail 四种元素处理**；
* **三条指令的非法指令判定**（通过 `VdotDecodeProbe` 比对香山译码阶段的真实判定逻辑，
  而不是我们自己复述一遍规则）。

### 10.3 本方案**真正覆盖不到**的部分

这些是全核 difftest 才能覆盖的，必须明说：

> **后续更新**：本节写于 P6，当时全核 difftest 未运行。之后全核 difftest（Level 2，MinimalConfig）已补做，
> 下表各行的全核实测结果见 `docs/stage3/23_全核difftest验证报告.md` §5、§7、§8（逐行以「更新」标注在「风险」列末尾）。

### 10.4 一句话的区别

> **本方案把全核 difftest 的 REF 侧原样搬了过来，把 DUT 侧从「整个乱序核」换成了
> 「vdot 功能单元 + 香山译码单元」。**
> 因此：凡是「一条 vdot 指令在给定架构状态下应该算出什么、应不应该报非法」这类问题，
> 本方案的结论与全核 difftest 等价；
> 凡是「这条指令在乱序流水线里被正确地发射/旁路/提交/投递异常」这类问题，
> 本方案一概不能回答。

后一类问题现由全核 difftest（Level 2）回答：`docs/stage3/23_全核difftest验证报告.md`。

## 11. 等价性论证，以及它的缺口

### 11.1 论证

1. **REF 完全相同**。本方案用的就是全核 difftest 会 `dlopen` 的那个 `.so`，
   同一套 C API、同一条 `difftest_exec(1)`。REF 侧没有任何近似。
2. **被比对的架构状态就是全核 difftest 会比对的那一项**。全核 difftest 比的是
   折算后的架构 `vrf`（`Preprocess.scala:35-55`），而 vdot 只写 `vd` 一个架构向量寄存器；
   本方案比的正是这个 `vd` 的 128 位。只要 `vd` 对，`memcmp(vrf)` 的那 512 B 就对
   （其余 31 个寄存器 vdot 不写）。
3. **DUT 侧的算术通路是同一份 RTL**。`VDotTop`（YunSuan 侧 FU 顶层）与 `VIMacU`
   （XiangShan 侧真正挂进流水线的 FU）复用**同样的 `VIMac64b.prod16` 抽头、
   同样的 `VDotTree` 例化、同样的 `accOperand` 选择、同样的 latency=2**
   （`VDotTop.scala` 头部注释，`docs/stage2/11_RTL实现说明.md` §2）。
4. **DUT 侧的译码/非法判定是同一份 RTL**。`VdotDecodeProbe` 里例化的
   `DecodeUnit` 与 `VecExceptionGen` 是未经任何包装的上游模块。
5. **比对链路被证明是有效的**。故障注入 6/6 被检出（RTL 侧 3、NEMU 侧 3，§8），
   并且 T3-RTL-2 这种只影响部分用例的一位错误也能被精确检出（写回结果的 bit0 翻转见补充项 T3-RTL-1b）。

### 11.2 缺口（必须承认的）

| 缺口 | 具体是什么 | 严重程度 |
|---|---|---|
| **G1 掩码/尾部成形逻辑在两个 FU 顶层里是两份代码** | `VIMacU` 复用香山的 `ByteMaskTailGen` + `Mgu`（`xiangshan.backend.fu.vector` 包，YunSuan 不可见），`VDotTop` 按同一行为表直接实现等价逻辑。**本方案验证的是 `VDotTop` 这一份**，`VIMacU` 那一份只在 L1 冒烟测试里跑过 golden model 比对 | **最大的一个缺口**。算术核心（乘法阵列+加法树）是同一份，但「把 `dotVd` 成形成最终 `vd`」的那 20 行在两处。**已在全核上闭合**：全核里挂进流水线的是 `VIMacU`，同一份 30758 条语料 0 失配，故障注入（`VIMacU` 结果 bit0 翻转）3/3 检出（`23` §6、§8） |
| **G2 没有背靠背流量** | 见 §10.3 第一行 | 中。**已在全核上闭合**（`23` §8） |
| **G3 `vcsr`/`mstatus.VS` 未纳入比对** | 见 §10.3 | 低–中。**已在全核上闭合**（`23` §8） |
| **G4 异常从译码到 ROB 的投递未验证** | 见 §10.3 | 低。**已在全核上闭合**（`23` §8） |
| ~~**G5 已知两类判定分歧尚未收敛**~~ | 首轮：§7.2（LMUL）与 §7.3（vdot4a vstart），在真实全核 difftest 上这两类配置会直接报 mismatch | **已收敛**：RTL 补 `dotEmulIllegal` + 语义修订 S-7'，复跑判定分歧 6415 → 0（§7.4），并由故障注入 `T3-NEMU-3` 守住不回退 |

**最诚实的表述**：本协同仿真证明了
「**在 LMUL=1、架构内可执行的全部配置下，香山的 vdot 功能单元与 NEMU 逐位一致，
且 SEW、vstart、LMUL 三条非法判定在全部 72758 条激励上逐条一致（分歧 0）**」，
它**不能**证明「把 vdot 集成进完整的昆明湖 V2 流水线后全核 difftest 一定干净」——
G1 那 20 行成形逻辑、G2 的背靠背时序，都是全核 difftest 会而本方案不会暴露的。
首轮发现的 G5（**确定会在全核上报错**的一类问题）已经在本层收敛，不再是全核 difftest 的已知障碍。

> **后续更新**：上面这段是 P6 时的表述。全核 difftest 之后已补做（`docs/stage3/23_全核difftest验证报告.md`），
> G1–G4 在 MinimalConfig 全核上实测闭合（`23` §8），包括 `vstart≠0` 在内的 4834 条应 trap 用例在全核上全部
> mcause=2，也印证了 G5 收敛后全核上不再出现判定分歧。仍未在全核上覆盖的是 LMUL≠1 的非法判定，
> 以及默认配置 / `KunminghuV2Config`（只构建了 MinimalConfig，理由见 `23` §3.1）。

### 11.3 为什么 P6 没跑全核 difftest，以及后来的补做

**P6 时的情况（历史记录，原文保留）**：

本机为 macOS/arm64、16 GB 内存、Docker VM 8 GB。
香山官方 `make verilog` 的 JVM 默认堆是 **40 GB**（`work/XiangShan-cosim/Makefile:81`
`JVM_XMX ?= 40G`），CI 的全核构建全部跑在自建服务器上且 `timeout-minutes` 给到 900；
Verilator 对全尺寸核的峰值 RSS 在社区经验里是 20–60 GB。
详细的可行性核算见 `docs/_recon/nemu-difftest-env.md` Part D 与
`docs/stage1/03_仿真平台搭建报告.md`。
因此 `MASTER_PLAN.md` D3 一开始就把全核 difftest 定为「有条件则补做」的延伸目标，
P6 阶段**未执行**，不伪造任何全核数据。

**后来的补做**：在 Linux x86_64 服务器（128 核、约 1 TB 内存）上完成了全核 difftest（Level 2），
报告见 `docs/stage3/23_全核difftest验证报告.md`。实测的资源需求印证了上面的判断：
MinimalConfig 全核 emu 构建有效耗时约 23 分钟，**Verilator 前端峰值 RSS 59.2 GB**
（`logs/stage3/fullcore/build_time_breakdown.log:34,39`），16 GB 机器确实做不了。

P6 时这里写的复现命令（`make emu CONFIG=MinimalConfig EMU_THREADS=2 ... -j8`，默认 g++）**实际会失败**：
difftest 子模块把 clang 专有选项 `-fno-slp-vectorize` 写死在 `OPT_FAST` 里
（`work/XiangShan-fullcore/difftest/verilator.mk:76`），g++ 直接报错（`logs/stage3/fullcore/build_emu.log:2421-2423`）；
改用 GCC 等价选项后 g++ 编译 Verilator 生成的超大函数又极慢（`23` §3.3）。现行复现方式：

```bash
# 依赖：scripts/00_setup_env_host.sh 已生成 work/XiangShan-kmhv2 与 work/NEMU；clang++；≥64 GB 内存
bash scripts/50_run_fullcore_difftest.sh build   # 全核树 + NEMU 私有副本 .so + emu（实测 23:31）
bash scripts/50_run_fullcore_difftest.sh run     # 6 批语料 + 依赖测试 4 个种子（实测约 45 分钟）
bash scripts/50_run_fullcore_difftest.sh wave    # 全核波形 + 文本轨迹 + 时序图
bash scripts/50_run_fullcore_difftest.sh fault   # 故障注入（首次需额外构建一次 emu）
```

**Level 1 在全核补做之后仍有独立价值**，不是被 Level 2 取代：

* **激励面更宽**：Level 1 跑了 72758 条激励，除与全核相同的 30758 条共享语料外，还有 `cosim_main.cpp` 现场生成的
  架构内随机 30000 条与非法面随机 12000 条（§4.3）；其中 LMUL≠1 的非法判定（§7.4 复跑 6000/6000 一致）
  只在 Level 1 覆盖，全核未复测（`23` §8）。
* **判定比对是逐条显式的**：Level 1 对每条激励单独记录 RTL 译码判定与 REF 是否抛异常，并按类别统计（§7），
  G5 的 6415 条判定分歧就是在这一层被量化并收敛的。
* **NEMU 侧故障注入**：Level 1 的 6 次故障注入中有 3 次改的是 NEMU（§8，含守护 S-7' 的 `T3-NEMU-3`），
  全核故障注入只改了 RTL（`23` §6）。
* **迭代快**：Level 1 缓存热时全流程约 1 分钟（§13），全核构建约 23 分钟、运行约 45 分钟。
